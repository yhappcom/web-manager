## 043 — Responsive Web Interaction, Input Modality & Cross-Device Continuity

`research/043-stage3-responsive-input-modality-cross-device-continuity.md`  
**FOUNDATION/PRACTITIONER CHECKPOINT: PASS.**

### Core model

Responsive correctness is **task/state contract preservation under changing geometry and input**, not screenshot similarity.

Retained judgment:
- viewport/layout width is not an input-device detector;
- `pointer`/`hover` describe the primary pointing device, while `any-pointer`/`any-hover` describe available pointing-device capabilities; none detects keyboard presence;
- narrow ≠ touch-only and wide ≠ mouse/keyboard-only;
- essential tasks/content must remain hover-independent;
- target/gesture accessibility requirements are not waived by `pointer:fine`;
- layout viewport and visual viewport can differ under pinch zoom and on-screen keyboards;
- browser chrome makes viewport height dynamic; small/large/dynamic viewport units have different behavior;
- VirtualKeyboard API is limited and should not be a core dependency without target-browser evidence;
- ordinary MintTap company/support/governance pages have no known essential orientation restriction;
- browser zoom, pinch zoom, text enlargement, localization growth and narrow reflow are distinct stressors;
- responsive visual reorder must preserve coherent source/focus/task sequence;
- in-progress action/form/retrieval state must survive responsive mode changes where technically applicable;
- cross-device continuity is a state/persistence question, not pixel continuity, and must not be promised without verified backend/session capability.

### Reusable output — Responsive/Input Continuity Contract

Specify task invariant, state invariant, layout trigger, input assumptions, hover dependency, pointer/gesture contract, keyboard/focus contract, visual-viewport behavior, orientation, zoom/reflow, responsive-state migration, URL/history, cross-device persistence boundary, progressive enhancement and browser/device/human validation matrix.
