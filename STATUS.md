## 163 checkpoint
- Deletion completion is a bounded claim over declared controlled domains/current generations, not proof that every copy everywhere has ceased to exist.
- Separate authoritative deletion, derived-store propagation, backup expiry/destruction and unmanaged/offline-copy status; do not collapse them into one `deleted` boolean.
- A monotonic deletion/retention generation or equivalent floor must dominate stale backups, exports, async jobs and reconnecting offline clients.
- Backup retention configuration predicts expiry; it does not itself attest destruction. Evidence strength depends on provider semantics, holds, recovery inventory, cryptographic topology and risk.
- Restore/PITR must recover and apply the current deletion floor before ordinary service reopens; restored indexes/jobs must be rebuilt/reconciled after that gate.
- Old exports can be authentic yet stale. Import integrity does not authorize resurrection into a lineage that is currently intentionally unavailable.
- Browser eviction/persistence and Service Worker cache cleanup are local storage mechanics, not governed fleet-deletion proof; Cache API cleanup does not imply IndexedDB/OPFS/export cleanup.
- An unreachable iPad neither proves fleet deletion failed nor proves it succeeded. Scope server claims honestly and reconcile the device when it returns.
- Unique unsynced local flight/user data is preserved when authority is ambiguous while stale remote lineage is blocked from automatic republish.
- Deletion-proof observability must itself be minimized so it does not become a permanent cross-system personal-data inventory.
