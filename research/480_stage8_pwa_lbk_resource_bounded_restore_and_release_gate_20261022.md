## History / problem → design principle → operational judgment

AppCache's opaque update model motivated programmable Service Workers, but application-shell recovery is not owner-ledger recovery. Studies [431](431_stage8_pwa_http_cache_vs_cache_api_update_contract_20261020.md), [437](437_stage8_pwa_control_catalogue_atomic_cutover_integrated_20261020.md) and [460](460_stage8_pwa_control_plane_authority_and_work_budget_20261021.md) separate HTTP cache, Worker control, Cache API catalogue and owner-data persistence. The newly merged B1 full-ledger `.lbk` engine creates a **new boundary**: a user-supplied, potentially large and unauthenticated interchange file must pass resource admission, schema/owner checks, fresh-staging preservation, local owner access and future remote Sync admission independently.

**Principle:** `file selected ≠ safe to parse ≠ integrity checked ≠ author authenticated ≠ owner authorized ≠ staging committed ≠ active ledger switched ≠ remote Sync approved ≠ independent backup verified`. A checksum is not a signature. A transactional staging restore is not an application cutover. A PWA's installed shell is not its irreplaceable owner record.

## SYNTHESIS — integrated ten-part admission and recovery contract

**I. File ingress before allocation.** A user-selected File exposes a byte size before its content is decoded. Reject obviously oversized files before whole-file UTF-8/JSON allocation. A product limit must be derived from real logbook corpus, memory/CPU tests and physical iPad constraints; **no numeric product maximum is established here**. MIME/extension is advisory, not trust. Ensure cancellation or rejection never mutates the active ledger.

**II. Parser work budget.** Bound total decoded bytes, aggregate row count, nesting depth, scalar/string lengths, object key lengths and validation time; validate strict UTF-8 and reject ambiguous duplicate JSON member names where the parser can support that. Existing B1 validates registry/row key duplicates **after** whole JSON parsing, so those checks do not cap pre-parse resource use. Any streaming/worker alternative must preserve canonical digest semantics and provide a bounded parser; moving parsing to a Web Worker does not make unbounded memory safe.

**III. Resource-accounting phases.** Track input File bytes, decoded UTF-16/string and JSON object graph, canonical re-encoding, digest work, transaction write amplification, staging database growth and optional temporary export copies as separate peak-memory/storage contributors. `navigator.storage.estimate()` is diagnostic, not an allocation guarantee. Handle quota failure and tab termination without deleting original data. Avoid declaring a universal safe size from desktop Chromium.

**IV. Integrity and authorship.** B1 SHA-256 detects accidental/unauthorized *changes relative to the supplied digest* but any file author can recompute it. It is not a MAC, digital signature, encryption, current server receipt or proof of a legitimate account. Verify authenticated current UID independently and preserve the original file in user custody; do not claim restored operations are server-authorized.

**V. Version compatibility.** Separate interchange format version (B1=1), source database capability (v16), current app schema, device replica identity and Sync protocol generation. Preserve original files for future migrations. Reject unsupported versions with a specific non-destructive explanation; do not silently coerce v16 into v17 or assume a checksum proves semantic compatibility.

**VI. First-run owner reservation.** A proposed restore choice must appear **before** either authenticated-owner creation path can bind a fresh ledger. Preserve SessionGate's remote check for restored Firebase sessions. Reservation alone is not a cross-tab lock: recheck destination emptiness and owner state inside the actual write transaction; old code paths and other tabs require explicit concurrency tests.

**VII. Staging and cutover.** Current B1 restores into a fresh staging DB and leaves the owner locked. The PWA opener still uses `logmate_ledger`. Engineering must decide whether to use a pre-owner empty primary DB or a separately named staging DB with an atomic-enough app-level selection/restart protocol; do not pretend a transaction spans two databases, browser contexts and file custody. No destructive replace/merge on an existing ledger without a separately approved contract.

**VIII. Remote Sync fence.** Imported outbox and revision IDs are historical local facts, not backend-applied receipts. Preserve logical operation IDs, require current owner authority and server-side idempotency/reconciliation before any explicit Manual Sync; offline recovery must not silently trigger network mutation. Backup import is not device-to-device unattended synchronization.

**IX. User/AT workflow.** B owns a minimal, truthful state sequence: `Choose existing backup → inspect compatibility/size → verify identity → import into empty staging → restart/reauthenticate → compare records → confirm independent backup → optionally request Manual Sync`. Explicitly label unsupported file, no space, wrong account, interrupted import and recovery choices; do not display `Restored` when only file parsing succeeded. Design Studio owns visual/interaction implementation and assistive-technology validation.

**X. Release provenance.** C/E require exact NORMAL archive with source SHA, toolchain, manifest/file digests, generated Worker and Hosting-served bytes. Acceptance artifact must be labeled non-deployable; a `build/web` directory left by an acceptance run is not a release candidate. Check Firebase `/__` Auth helpers, update/rollback, mixed Worker versions, Safari tab/Home Screen and managed-iPad storage identity independently. Owner-data restore must pass even when offline shell repair is degraded.
