## 1. Decision: keep deep research, stop reflexive repetition

**Recommended cadence:** retain the existing **hourly trigger** for now, but **one integrated, high-information-gain substantive research cycle per activation**. Hourly is a wakeup, not an automatic one-file/one-topic quota or claim of work for 60 minutes. Source changes, independent falsification, contradictions and real product decisions define meaningful checkpoints. There is **no requirement to generate a Git commit or user message every hour**.

**Failure pattern to eliminate:** “Re-read HEAD; same 37/29 risk; no fresh runtime PASS; HOLD; next same test” repeated across consecutive cycles is useful once but is **not** continuing professional learning. If the top P0 is externally blocked and no new evidence is accessible, record the blocker once, then investigate the next **independent, actionable** Stage 8/PWA question or an underdeveloped B/C/D bridge. Revisit P0 on material product/source/Engineering evidence, not every hour by rote.

## 4. Per-run substantial integrated packet (8–12 older blocks as a heuristic, not a checklist quota)

A good cycle selects *one connected failure domain* and investigates:
- history/misconception and a specific operational failure hypothesis;
- authoritative standard or current platform implementation, with source date;
- exact product/source alignment only if authorized/available;
- at least two contrasting failure cases/negative controls;
- cross-track E/A/C/B/D dependency or contradiction (owner vs consumer);
- evidence classification and viable falsification/acceptance procedure;
- decision or explicit OPEN with independent prerequisite;
- changed source/research index/evidence register iff material; otherwise no duplicate commit.

A packet **may** contain several adjacent subquestions (scope/identity, permission, storage, user state, error/repair, test oracle and handoff). It should stop at a coherent decision boundary, not after the first small paragraph. Do not fabricate additional material to fill volume.

## 5. Automation choice and escalation policy

**Default recommendation:** keep **one Web Manager hourly scheduled task**, not five micro-track tasks. The task should use this file and the masters as navigation, always inspect original evidence when a claim matters, and stay in read-only mode for Product/Design/Marketing/Engineering. Web Manager research integration can be written to **its own** repository only when material and authorized by repository rules.

**Periodic editorial maintenance within that same hourly task:** choose the first suitable run each **week** to check evidence freshness, contradicted studies, dead links, outdated top-of-file STATUS and missing cross-links. Make **monthly** or material-version-change audits for source/claim/OS/Browser/policy drift; a monthly label alone does not authorize changing release gates. These are **work categories**, not new scheduled tasks or changed schedules.

**Saturation/pivot:** when two consecutive runs find no new primary evidence for the same blocked gate, stop repeating the static audit until HEAD or another relevant dependency changes. Take the next ranked independently answerable question; if no source/authority for any meaningful question, record one concise blocker rather than inventing work. Reassess whether hourly remains worthwhile; only on owner approval change cadence (for example 3–6 hours) or create a separate weekly review task.

**Release/Engineering escalation:** A high-severity source-only risk goes to an owner with source SHA, exact failing predicate, test packet and privacy-safe synthetic fixtures. Web Manager does not modify LogMate code, execute destructive tests on real EFBs, claim defects from models, or change a peer's canonical policy.

## 6. Write and report protocol (anti-noise)

- **Update one existing integrated research artifact** when deepening a prior domain; start new integrated research only for a materially new domain/boundary. Do not generate a stream of 1-question files.
- **Update a master** only when a canonical conclusion, source supersession, major dependency/owner boundary or validation class changes; retain original citations and distinguish SOURCE/SYNTHESIS/MINTTAP DIRECTION/OPEN/VALIDATION/CHANGE WATCH.
- **Update [Evidence Register](EVIDENCE_VALIDATION_REGISTER.md)** on an actual source contradiction or new executable test result; source SHA / test run / platform and applicability limit mandatory.
- **Update [STATUS](../../STATUS.md)** only on gate/priority change, meaningful integrated checkpoint, or switching major subject. Preserve historical paragraphs; keep short *current* summary at top.
- **Update [research index](../README.md)** only for a meaningful addition/changed navigation; avoid a new hourly bullet for a HEAD check with no new insight.
- **Report to owner** material bundled insight, proof/limit, gate change (or no change), cross-team handoff and next major target. Do not publish micro-updates merely because an hourly task fired.
- **No duplicate commits:** file count, section count and CI job count are not learning success metrics. Success is changed decisions, reduced uncertainty or independent contradictions resolved.

## 7. Verification and amendment triggers

Promote a gate only when primary test conditions and source/version scope are actually met and approved by the owning product/Engineering authority. Reopen synthesis if a new WebKit/iPadOS capability changes allowed operations, a current product source eliminates the 37/29 gap, exact Dart/IndexedDB/device tests contradict static predictions, a peer's canonical product policy changes, or current website/Store operator data becomes available. Preserve original studies as an audit trail; never silently rewrite legacy PASS/FAIL chronology.
