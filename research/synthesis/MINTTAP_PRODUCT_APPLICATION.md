### 8.1 Exact implementation facts and limits

| Boundary | Inspected implementation | What remains unproven |
| --- | --- | --- |
| B1 writer | `exportWholeLedgerBackup(verifiedOwnerUid)` executes a Sembast transaction, checks READY, matching unlocked bound owner and non-locking deletion state, reads `_syncLbkStoreRegistry` (30 base + seven Sync stores), serializes a manifest with owner UID, source replica, schema version, registry/counts and `snapshotDigest`; returns a `Future<String>` | Whether a UI saves that string to independent Files, whether all call sites enforce verified Firebase UID, resource/performance limits on real iPad |
| B1 reader | `restoreWholeLedgerBackup(String, verifiedOwnerUid)` decodes/validates before a transaction, requires empty staging destination, preserves newly generated destination replica, installs locked matching owner, resets imported Sync trust and supports legacy v1 conversion | Whether a supported file picker and actual PWA/native UI reach this reader; independent fresh-device restore and process-interruption evidence |

| Integrity | `lbkSha256` is an unkeyed SHA-256 checksum, documented as integrity-only | Digest alone does not authenticate origin, ownership, historical freshness or protect confidentiality; owner/registry/Sync semantic checks are separate |
| File custody | Writer returns text and reader accepts text; adapter explicitly says caller owns file selection and I/O | User-controlled Files save/reopen, MDM Managed Open In policy, persistence after browser eviction, and portable recovery remain OPEN |

**SYNTHESIS / failure chains:** (1) Valid JSON and matching digest can be regenerated by anyone holding the plaintext file; thus checksum is corruption detection, not proof that a backup came from an authorized account. (2) A returned string is not a durable backup: the file chooser may be canceled, managed transfer blocked, or browser process terminated before external persistence. (3) A coherent transactional snapshot is not a proof of nonblocking UI, bounded heap use or filesystem atomicity; serialization and SHA computation are performed within the export transaction. (4) Imported Sync receipts/cursors are explicitly downgraded/reset by the reader, so a successful restore must not be advertised as remote synchronization. (5) A backup from before deletion/tombstone events requires separate policy for stale-data resurrection; the codec digest does not enforce recency.

**MINTTAP DECISION / scoped:** Treat the current inspected B1 interchange as **structured JSON with checksum and explicit owner validation**, not as an encrypted, authenticated or independently saved file. This is a description of inspected source, **not** a production-feature approval or public privacy claim. The prior §36 encryption/key-loss analysis remains conditional only. Do not add encryption or change file format without product/Engineering authority and migration/recovery planning.

**SOURCE / read-only pinned evidence:** LogMate [whole-ledger codec](https://github.com/yhappcom/logmate/blob/main/lib/repository/logbook/whole_ledger_backup.dart) blob `711f784534bc686a4d8edd6617ac4d1ac362e0a7`; [Sembast repository](https://github.com/yhappcom/logmate/blob/main/lib/repository/logbook/sembast_logbook_repository.dart) blob `f2b8b0eb681f5d960532dac5c87b29cf85a459b8`. These are source observations, not execution. Design Studio [WEB_STATUS](https://github.com/yhappcom/design-studio/blob/main/progress/WEB_STATUS.md) blob `265433cdb585a3fd5fd414cce54cf11462287715` still requires exact runtime/device evidence; Marketing [STATUS](https://github.com/yhappcom/marketing-manager/blob/main/STATUS.md) blob `d9cd4f691d7f666d6a258aa9be292d4cbdec797e` records no new production approvals. The other repositories were read-only.

**History/problem → principle:** Portable backup must survive a chain of independent boundaries: coherent snapshot, exported bytes, independently retained Files artifact, authenticated/authorized fresh staging restore, validated staged ledger, safe promotion to the app's active database, cold-relaunch readback, and separately authorized Sync. Passing one boundary does not imply the next. AppCache/Service Worker cache and browser origin storage are not independent Files custody.

**Current implementation / exact source predicates:**
1. `exportWholeLedgerBackup` runs under a Sembast database transaction, checks READY capability, matching unlocked owner and deletion lock, enumerates `_syncLbkStoreRegistry`, emits v2 manifest plus digest and returns a **String**. This is a coherent repository snapshot under the transaction, **not** evidence of external save, disk flush or byte-for-byte reopen.
2. `restoreWholeLedgerBackup` decodes and validates before entering a Sembast transaction. It calls `_requireEmptyLbkDestination`, writes registered stores inside the transaction, retains the destination replica ID, binds the matching owner in an explicitly **locked** state, resets local Sync apply authority and validates restored references before transaction completion. The test-only `afterStoreWritesForTesting` hook occurs inside that transaction and can support a rollback oracle.
3. `_requireEmptyLbkDestination` checks named active/deleted/revision/outbox/sync stores plus initial structure, baseline, configuration, unbound owner, local entry and Sync state. It is a **fresh staging** precondition, not a generic merge-into-existing-ledger API. The code does not itself demonstrate an application-level atomic switch from staging database to active database.
4. `WholeLedgerBackup.decode` accepts JSON and normalizes map keys to strings. `_validateLbkContainer` checks manifest, digest, registry/count/type, duplicate row keys, owner and replica metadata, and v2 Sync evidence. SHA-256 detects ordinary corruption but does **not** authenticate authorship or prevent deliberate re-computation by an adversary. No source-level assertion of a maximum import byte size, resource budget or untrusted-file streaming limit is established by these inspected functions; do not assert the entire application lacks such controls.
5. v1 import is handled through a distinct legacy registry/Sync reset branch. v1/v2 compatibility and failure containment need independent oracles; a successful v2 synthetic test cannot certify v1 migration or an actual deployed Web build.

**SYNTHESIS / failure-chain and cross-track contradictions:** A transaction-level rollback can succeed while the application still loses data if a caller replaces the active DB before staging/cold verification; an independently saved file can be readable but wrong-owner; a valid digest can be forged; a restored local ledger can be coherent while remote Sync remains unverified. Conversely, the visible empty Settings callback (§9) does not refute the existence of the repository-level restore implementation. Preserve all these distinctions.

**MINTTAP DECISION (research recommendation, not owner approval):** Keep the active ledger untouched until fresh staging restore, owner/epoch admission, full inventory/reference validation and cold-relaunch readback succeed. Require a separately reviewed promotion/switch contract and failure-recovery path before calling the workflow a user-usable restore. Never use a successful repository transaction as proof of external Files custody or of a safely promoted PWA.
