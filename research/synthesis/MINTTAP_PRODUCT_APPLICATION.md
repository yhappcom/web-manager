| Boundary | Inspected implementation | What remains unproven |

| Integrity | `lbkSha256` is an unkeyed SHA-256 checksum, documented as integrity-only | Digest alone does not authenticate origin, ownership, historical freshness or protect confidentiality; owner/registry/Sync semantic checks are separate |
| File custody | Writer returns text and reader accepts text; adapter explicitly says caller owns file selection and I/O | User-controlled Files save/reopen, MDM Managed Open In policy, persistence after browser eviction, and portable recovery remain OPEN |

**SYNTHESIS / failure chains:** (1) Valid JSON and matching digest can be regenerated by anyone holding the plaintext file; thus checksum is corruption detection, not proof that a backup came from an authorized account. (2) A returned string is not a durable backup: the file chooser may be canceled, managed transfer blocked, or browser process terminated before external persistence. (3) A coherent transactional snapshot is not a proof of nonblocking UI, bounded heap use or filesystem atomicity; serialization and SHA computation are performed within the export transaction. (4) Imported Sync receipts/cursors are explicitly downgraded/reset by the reader, so a successful restore must not be advertised as remote synchronization. (5) A backup from before deletion/tombstone events requires separate policy for stale-data resurrection; the codec digest does not enforce recency.

**MINTTAP DECISION / scoped:** Treat the current inspected B1 interchange as **structured JSON with checksum and explicit owner validation**, not as an encrypted, authenticated or independently saved file. This is a description of inspected source, **not** a production-feature approval or public privacy claim. The prior §36 encryption/key-loss analysis remains conditional only. Do not add encryption or change file format without product/Engineering authority and migration/recovery planning.

## 18. HTTP no-store versus programmable PWA cache and destructive session cleanup (2026-11-09)

**SOURCE — standard/platform, checked 2026-11-09:** [RFC 9111 §5.2.2.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5) defines HTTP `Cache-Control: no-store` for HTTP caches, not as a general browser data-erasure or authentication boundary. [MDN Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache) explicitly states that the programmable Cache API **does not honor HTTP caching headers**; application/Worker code controls which Request/Response pairs are stored. [MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching) distinguishes managed caches, existing stale entries, `no-cache` revalidation, `no-store` storage prohibition, and the performance cost of indiscriminate `no-store`. [MDN Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data) identifies `"storage"` as affecting IndexedDB and Worker registrations where supported; [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) recommends protecting sensitive session responses and session invalidation. These mechanisms operate at different layers and cannot be treated as interchangeable.

**SOURCE — read-only product configuration:** LogMate [`firebase.json`](https://github.com/yhappcom/logmate/blob/main/firebase.json), inspected 2026-11-09, applies `Cache-Control: no-cache, no-store, must-revalidate` through a Hosting `source: "**"` rule and declares three `/auth` email-action rewrites. [`web/index.html`](https://github.com/yhappcom/logmate/blob/main/web/index.html) loads `flutter_bootstrap.js` and a manifest through relative paths. This proves **repository configuration only**, not served header precedence on reserved Firebase routes, CDN responses, generated build/Worker content, installed client control, or offline execution. The `no-store` directive is controlling for conforming HTTP caches; it **does not automatically prohibit an explicit Service Worker Cache API `put()`**. Conversely, the presence of a Worker or a cache entry does not prove a usable offline shell. Whether Flutter's generated Worker exists and what it caches is build-dependent and OPEN.

**SYNTHESIS — two independent hazards:** (1) Treating the global Hosting header as proof that OAuth/email action responses, deletion status or owner-sensitive resources cannot be saved anywhere is unsafe: an in-scope Worker may programmatically store responses, and history/bfcache, JS state and IndexedDB have distinct rules. (2) Treating a generic security response such as `Clear-Site-Data: "storage"` as a harmless logout/incident remedy is unsafe for a local-first EFB: it can delete the **only** unsynced 37-store ledger and unregister the offline Worker, with no independent Files backup proven. These are conditional architectural hazards, **not observed LogMate leakage, cache defect, or data loss**. A legitimate need to revoke session authority is not equivalent to permission to erase local flight records. Cache behavior and data custody must be independently tested.

**MINTTAP DECISION — recommended boundary, not an approved implementation:** Classify routes/resources by content and authority before selecting cache policies: public immutable versioned shell assets; mutable HTML/manifest/Worker; one-time email/OAuth callbacks; private deletion/account status; authenticated data/API responses; local IndexedDB ledger and independent Files backup. Require explicit deny-by-default Worker cache admission for callback URLs, query-bearing one-time codes, authenticated API/status responses, and user-private documents; never rely solely on HTTP headers for Cache API exclusion. Keep public offline shell availability separate from secret-bearing responses. Prefer a narrowly scoped session revocation and owner/epoch write fence over site-wide storage clearing; destructive origin wipe requires product-owner authorization, verified independent recovery and 37-store acceptance. Do not alter the existing Hosting header, Worker, Firebase routes or LogMate product policy from this research.

## 19. Service Worker fetch-admission and offline fallback trust boundary (2026-11-09)

**SOURCE — current browser/platform documentation (checked 2026-11-09):** [MDN ServiceWorker fetch event](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/fetch_event) states that a controlled navigation and its subresources can be intercepted, and a handler that does not call `respondWith()` falls through to normal fetch. [MDN respondWith](https://developer.mozilla.org/en-US/docs/Web/API/FetchEvent/respondWith) documents response-type/mode restrictions and that navigation may receive alternate content while retaining the requested URL. [MDN Using Service Workers](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers) explains installation/precache, `waitUntil()` for asynchronous writes, `preloadResponse`, and fallback behavior. [Google web.dev HTTP versus SW cache strategies](https://web.dev/articles/service-worker-caching-and-http-caching) distinguishes browser HTTP cache from programmable Worker strategies. Combine with §18 [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html) and [MDN Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache): HTTP `no-store` is not a Cache API admission rule. These are generic mechanisms, **not a deployed LogMate result**.

**HISTORY / PRINCIPLE:** AppCache's implicit resource manifest model did not provide adequate per-request policy or update control; programmable Worker fetch interception permits explicit decisions, but makes cache admission, navigation fallback, version transitions and security boundaries application responsibilities. A shell being available offline is not evidence that an authenticated operation, an ownership decision or a destructive account action completed.

**SYNTHESIS — request classification before response strategy:** For each intercepted request, consider *origin, method, URL path, query, navigation mode/destination, credentials, response status/type/redirect and owner-sensitive content* before any `Cache.put()` or offline fallback. A generic “cache every successful GET” or “serve index.html for all navigations” can create a conditional risk of displaying a shell on an authentication callback, deletion-status URL, nonexistent public route or owner-specific page. A navigation fallback can preserve the original URL in the address bar even when serving different HTML; therefore a visually rendered app shell is not proof that the requested resource existed or the callback succeeded. The presence of a `fetch` handler does not prove every request is controlled, nor does `waitUntil()` establish successful persistence without checking its outcome. Navigation preload, if enabled and supported, is a network response path requiring the same response-admission rules as ordinary fetch.

**MINTTAP DECISION — recommended policy matrix, not implementation approval:**

| Resource class | Suggested Worker behavior | Evidence/negative control |
| --- | --- | --- |
| Immutable versioned public assets | Integrity/version-qualified cache admission; fail closed on missing/mismatched asset | Exact built/served asset bytes and V1/V2 cache inventory |

| OAuth/Firebase email-action callback and one-time codes | Bypass application cache; no offline success substitution | Query-code canary absent from Cache API, history/referrer/telemetry |
| Account deletion/status and private API | Network/authorization only; fail with truthful unavailable state | Expired token, owner A→B, cached-200 and offline negative tests |

**FAILURE / CONTRADICTION diagnostics:** (1) `request.mode === "navigate"` alone does not distinguish an app route from an OAuth callback or public policy URL; route allowlisting is essential. (2) URL-only cache keys cannot be assumed to enforce owner identity; response `Vary` and request matching are not substitutes for authorization. (3) An opaque cross-origin response is not inspectable like a same-origin authenticated response; never classify it as safe merely because it can be cached. (4) HTTP status 200, `navigator.onLine`, a registered Worker, a `preloadResponse`, and a rendered shell are separate signals, none proving durable data custody. (5) Clearing CacheStorage alone is not a safe or complete logout; clearing all site storage may erase unsynced ledger (§18). (6) A cached HTML shell may be legitimate offline while authenticated APIs correctly fail; UX must show that distinction rather than fabricating sync success.

**SOURCE — standards/platform, checked 2026-11-09:** [MDN NavigationPreloadManager](https://developer.mozilla.org/en-US/docs/Web/API/NavigationPreloadManager) and [MDN Service Worker usage](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers) describe navigation requests started in parallel with a waking Service Worker and subsequently available through `FetchEvent.preloadResponse`. ## 32. Stage 8 Clear-Site-Data and logout: browser-wide erasure is not owner-scoped custody (2026-11-10 KST)

**SOURCE — standards, not product runtime:** [W3C Clear Site Data](https://www.w3.org/TR/clear-site-data/) defines an HTTP response header that can request user-agent clearing of categories such as `"cache"`, `"cookies"`, `"storage"`, and `"executionContexts"`. [MDN Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Clear-Site-Data) documents browser-specific support and behavior; support and exact effects require versioned verification. [Service Workers](https://w3c.github.io/ServiceWorker/) and [Storage Standard](https://storage.spec.whatwg.org/) separate registrations, origin storage and execution contexts from application-defined account ownership. This section is a **new threat-model analysis**, not an observation that LogMate sends the header. No current deployed response or product implementation was inspected for this header in this section.

**HISTORY / DESIGN PRINCIPLE:** A server can request origin/site-related browser data clearing after a compromise or sign-out, but an offline-first ledger needs explicit data custody. Browser clearing is not a transaction over Firebase UID, replica ownership, export inventory, remote deletion saga or a user-controlled Files backup. In a shared-origin or multiple-account PWA, a site-data wipe may remove **unsynced records belonging to the current or another local owner**, while a cookie-only logout may leave prior-owner records and controlled tabs intact. These are opposite hazards; neither a blanket wipe nor no wipe is automatically correct.

**SYNTHESIS — threat/failure matrix (E owner, A dependency):**
1. **Logout with pending offline writes:** a `"storage"` clearing response may destroy unsynced IndexedDB data before a successful, independently verified export/restore. A browser's acceptance of the header is not an application-level deletion receipt.
2. **Owner A→B switch:** clearing origin storage is not evidence that A's remote writes were revoked, old controlled tabs stopped, duplicate replicas were invalidated or all 37 local stores were inventoried. Conversely, absence of clearing does not prove a leak.
3. **Auth action route:** attaching the header indiscriminately to `/auth/action` could erase the app's same-origin offline ledger during email verification or password reset. Header route policy must be tested against exact origin and redirect chain, not inferred from HTML rewrites.
4. **Compromise response:** emergency cache/storage clearing can be a defensible containment option, but may be unacceptable without recovery, incident authorization and independent backup. Do not promise it can recover already-exfiltrated data.
5. **Installed iPad:** Safari tab, Home Screen app and managed Web Clip may have distinct containers and header support; one browser test cannot prove all containers were wiped or preserved. MDM removal is a separate OS/operator action.
6. **Cookie semantics:** browser cookie deletion, Firebase session invalidation, owner authorization, IndexedDB deletion and Files custody are different controls. Clearing client cookies alone does not revoke already-issued backend credentials or deny an old writer.
7. **UX and analytics:** “signed out,” “local data removed,” “cloud deletion completed,” and “backup recoverable” require separate observed receipts. A privacy event must not include owner IDs, flight data or sensitive URLs.

**MINTTAP DECISION — research proposal only:** Do **not** introduce a global `Clear-Site-Data` header as a shortcut for logout, account deletion, security hardening or OAuth repair. Define a route- and incident-specific admission decision with Engineering and the product data owner, preserve unsynced ledger custody, and require negative tests before enabling any destructive directive. Emergency response should explicitly distinguish session revocation, origin/container erasure, remote deletion, independently recoverable Files and rollback feasibility. No change to LogMate code, Hosting, Marketing claims or user data is authorized.

**VALIDATION CD01–CD16 — DEFINED, NOT EXECUTED:** CD01 inventory actual deployed headers per route and redirects; CD02 pin exact browser/OS/managed policy; CD03 create disposable synthetic owner A and 37-store canaries; CD04 prove offline unsynced writes exist before logout; CD05 test logout without site-data clearing; CD06 test isolated `"cookies"` behavior; CD07 test `"storage"` only in disposable origin; CD08 test `"cache"` independently; CD09 test `"executionContexts"` support and old tabs; CD10 exercise email action/redirect and verify no accidental wipe; CD11 verify A→B owner and old-writer denial at transaction/remote admission; CD12 verify server-side token/session invalidation separately; CD13 test Safari tab versus installed Home Screen versus approved Web Clip; CD14 test offline reload, quota, interruption and update rollback; CD15 export then restore to fresh container from independent Files, with 37-store parity; CD16 record redacted expected/observed outcomes, source SHA, rollback and product-owner sign-off. A header's presence or a browser storage estimate is **not** a CD PASS.

**TRANSFER / CONTRADICTION / DEPENDENCY / CHANGE WATCH:** **E** owns incident policy, data-custody and route-header admission; **A** owns header processing, origin/site scope and browser differences; **C** owns destructive-test fixtures and reproducible accessibility/device evidence; **B** owns truthful logout/deletion/recovery copy and interrupted-flow UX; **D** owns privacy-safe analytics and avoids false deletion claims. **CONTRADICTION:** a generic “clear all site data on logout” security recommendation can conflict with the product's offline-first and independent-backup requirements. **DEPENDENCY:** exact served headers, disposable origin, Engineering-owned 37-store and old-writer fixture, authorized managed iPad. **CHANGE WATCH:** browser support and semantics for directives, Safari container isolation and Firebase session behavior. **GATES UNCHANGED: Stage 8 ACTIVE · Production validation OPEN · PWA release HOLD.**

## 34. Stage 8 discovery/canonical and sensitive-action indexing boundaries (2026-11-10 KST)

**SOURCE — source-pinned read-only product inspection:** LogMate `web/about/index.html` blob `947aae8889a5e931724af0b7bfc989d35d88c7af` declares `<link rel="canonical" href="https://logmate.minttap.app/about">` while the Marketing 2026-11-09 independently observed successful public `/about/` response; `web/account-deletion/index.html` blob `f8558e921c3f72743189a82d6f9cefe81b6fb193` similarly declares slashless `/account-deletion`, with internal footer links also slashless. These are **two distinct evidence types**: repository-declared canonical preference and peer-observed slash-suffixed page reachability. Neither proves the redirect/status/body/canonical selected by Google. `web/auth/action/index.html` blob `39d06a633ab7bee719b3401bc3ac744f8ba175d0` contains `<meta name="robots" content="noindex">`; `firebase.json` blob `9ac0972e26749215c4a718360c66315c6caf3cc8` rewrites `/auth`, `/auth/`, `/auth/action` to the account-action HTML. This is not evidence that the deployed host returns 404, nor that generated files or alternate paths are absent. No live Search Console, deployed header, crawl or token URL trace was executed in this run.

**PRIMARY STANDARD / PLATFORM:** [Google Search Central canonical methods](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) ranks redirects and HTML canonical as strong signals and sitemap as weaker; canonical is a **hint**, not a server redirect, an authorization boundary or guaranteed search-selected URL. [Google noindex documentation](https://developers.google.com/search/docs/crawling-indexing/block-indexing) and [robots meta specification](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag) require crawlers to be allowed to fetch the HTML/header to discover `noindex`. A `robots.txt Disallow` that prevents fetching an account-action page can defeat discovery of its `noindex` directive. Conversely, `noindex` is not confidentiality, does not invalidate Firebase one-time codes, and does not remove sensitive query strings from browser history, referral/telemetry or server logs. Search control, credential secrecy, and public-support discoverability are **three separate** responsibilities.

**SYNTHESIS / FAILURE MODES:** (1) slashless canonical plus slash-suffixed HTTP 200 may be benign duplicate routing or may fragment Search Console reporting depending on actual redirects and Google selection; (2) a crawler fetching a rewrite under `/auth` may see `noindex`, but only exact served route+redirect+worker evidence can establish this; (3) robots blocking `/auth` can make the intended noindex unreadable; (4) a worker fallback that returns Flutter shell to a public `/about/` navigation can change the served title/canonical/robots content despite static source correctness; (5) canonicalizing token-bearing action URLs cannot sanitize credentials or make them safe to log; (6) indexing a public account-deletion **instruction** page is potentially useful for user rights and store-policy discovery, while indexing a **personal account-action** page is inappropriate. Do not indiscriminately noindex all account-related URLs.

**MINTTAP DECISION — proposed web requirement, NOT a deployment instruction:** Select one stable public canonical route style per trust page only after verifying real redirect chains and served content; align internal links and any sitemap to that choice. Keep public About/Privacy/Terms/Support/Account-deletion instructions discoverable according to product/legal review; keep one-time-code action routes `noindex` and protect actual credentials via route-specific referrer/logging/history controls. Do **not** use `robots.txt` to hide token pages, do **not** treat canonical as a redirect, and do **not** modify LogMate routing/headers or promote marketing claims without product-owner and Engineering review.

Design Studio W121 is a UX execution dependency, not indexing evidence. **CONTRADICTION:** blanket `robots.txt Disallow: /auth` can conflict with the page's existing `noindex`; a blanket `noindex` on public account-deletion guidance conflicts with its discoverability purpose.
