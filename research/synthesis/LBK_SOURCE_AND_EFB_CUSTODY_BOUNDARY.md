The codec explicitly describes itself as a **narrow integrity container, not encryption or author authentication**. `WholeLedgerBackup` serializes a JSON object with exactly `manifest` and `stores`, sorts map keys recursively using Dart string comparison, accepts versions 1 and 2 as constants, and provides an internal SHA-256 helper over UTF-8. This establishes **codec behavior**, not a claim that every exported file is valid or that checksum alone authenticates a sender. In particular, an attacker who can change both payload and unkeyed checksum is not stopped by SHA-256.

The test file contains source-visible cases for a populated v16/v1 fixture, 30-store legacy import, version-17 destination schema, destination replica preservation, owner locked after restore, tamper rejection, transactional rollback/retry, occupied destination rejection and duplicate store-key rejection. These are **test definitions at the pinned SHA**; historical executed native tests are separately indexed in [Evidence Register EV06](EVIDENCE_VALIDATION_REGISTER.md). Reading a test file does not constitute executing that test today.

The approved Sync contract requires a structured `.lbk` full-ledger transfer, verified UID, owner-safe fresh replica, no silent overwrite of an occupied ledger, and separately authenticated Manual Sync. It explicitly distinguishes the current contract from implemented full backup, P2P and production deployment. It does not authorize treating `.lbk` as encrypted, externally stored, or safely restorable on a managed EFB.

## SYNTHESIS — three trust boundaries and counterexamples

1. **Container integrity vs confidentiality/authenticity (E owns).** A valid JSON manifest and recomputed SHA-256 detect accidental mismatch but cannot establish an authorized author or hide flight records. Do not label an unencrypted export “secure backup” without separate protection, transport and custody evidence. Wrong-owner checks and destination zero-write must be verified at the repository admission boundary, not inferred from `decode()`.
2. **Repository restore vs independent Files custody (A/E/C).** In-memory/native Sembast tests can demonstrate a transaction rollback and owner/replica invariants, but cannot establish a managed iPad can save, locate, reopen and restore a file after the PWA origin/profile disappears. Export generation, Files save, independent readback and fresh-container restore are four different checkpoints.
3. **Historical v1/v2 vs current 37-store inventory (E/C).** A 30-store v1 fixture and an updated destination schema do not establish current v2's complete 37-store transfer, deletion parity, pending/receipt/cursor integrity or cross-platform codec equivalence. The [37-export/29-drop static concern](../529_stage8_pwa_owner_deletion_backup_mdm_custody_20261030.md) remains a **separate** deletion gate; backup completeness cannot be inferred from that count alone.

## 2026-11-10 exact repository admission and restore transaction refinement (SOURCE → TRANSFER)

**SOURCE — pinned LogMate `main@f4bcd2f7b7e77039e29653baa1cc93797673885b`, Sembast repository blob `f2b8b0eb681f5d960532dac5c87b29cf85a459b8`, lines 450–632 and 6180–6405.** [Exact repository source](https://github.com/yhappcom/logmate/blob/f4bcd2f7b7e77039e29653baa1cc93797673885b/lib/repository/logbook/sembast_logbook_repository.dart). The following are static observations, **not** executed tests:

- `exportWholeLedgerBackup(verifiedOwnerUid)` requires READY capability, matching unlocked bound owner, and no deletion phase locking normal access **inside a database transaction**. It enumerates the full `_syncLbkStoreRegistry`, clones rows, creates a manifest with source schema, owner, replica and store counts, then hashes the canonical unsigned JSON and returns the complete encoded `.lbk` **string**. The source explicitly assigns file selection and I/O to its **caller**. Hence successful repository export is neither a user-visible file-save nor an independently durable Files backup.
- `restoreWholeLedgerBackup(encodedBackup, verifiedOwnerUid)` decodes and validates the untrusted container **before** entering the destination transaction. Within the transaction it requires an empty destination, preserves the destination replica, writes each registered store, re-locks the verified owner, resets Sync authority and revalidates invariants. The test-only fault seam is inside the transaction. A failed validation or transaction is intended to prevent partial publication, but only exact runtime/reopen tests can establish the behavior of the target adapter.
- `_validateLbkContainer` checks version/schema, exact owner UID, 64-hex source replica, ordered registry/count/key types, unique keys, complete store inventory, digest, owner/replica row references and v2 Sync evidence. `_validateLbkSyncEvidence` checks nested owner references and canonical Sync payload digest/identity fields. **An unkeyed digest is not author authentication**, and nested semantic checks do not make arbitrary input safe against resource exhaustion. The pre-transaction JSON decode/digest/row iteration is a separate memory/CPU/availability boundary from the transactional mutation boundary.
- `_resetRestoredSyncTrust` moves restored cursor/applied-identity evidence into recovery holds, rejects recovery-hold key collisions, drops source cursor/applied-identity stores, and establishes a destination-local unbound/unverified Sync state. Therefore **restore success is not remote synchronization acknowledgment**; the retained source evidence must not be represented as already applied or server-confirmed.
- The code path alone does not identify the Flutter Web UI export/share adapter, browser file handle, actual iPad Files destination, OS-managed restrictions, or runtime performance on a populated 37-store ledger. These remain **OPEN**; do not infer implementation absence from the uninspected caller.

**SYNTHESIS / operational judgment:** There are at least five independently testable boundaries: (1) transaction-consistent snapshot; (2) complete encoded bytes; (3) caller-side file publication; (4) independent readback/hash after app-container loss; (5) fresh-destination semantic restore plus cold reopen. Reporting any earlier boundary as “Backup complete” is misleading unless the product explicitly defines that narrower meaning. Large transaction-held cloning/hash/encoding and pre-transaction untrusted decoding are **conditional performance/resource risks**, not measured incidents.
