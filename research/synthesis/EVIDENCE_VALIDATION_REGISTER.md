## 1. Mandatory evidence taxonomy

| Code | Meaning | Can establish | Cannot establish |
| --- | --- | --- | --- |
| **G** generic competency PASS | Sequenced curriculum, standard/source reasoning and exercises | Research maturity | Product/deployment readiness |
| **S** SOURCE pinned/static | Named source path/blob/commit and inspected implementation predicate | Source-level contract/gap at that SHA | Runtime reachability, user incident, physical behavior |
| **M** MODEL or SYNTHESIS | Reasoned mechanism, simulated counterexample, threat/failure model | Possible interleaving and an actionable test oracle | Real-browser/LogMate execution |
| **R** research-only executable PASS | CI fixture + exact platform/versions + checked log/outcome | Mechanism in that tested fixture | Canonical NORMAL product, other OS/browser, full app |
| **H** historical exact product/component PASS | Exact old product checkout/CI/component | Only executed scenario/build on that platform | Newer `main`, installed/managed iPad, missing feature classes |
| **D** device/production execution | Independent source-pinned actual served/installed/managed environment with test data | Scope of actual tested device/build/journey | All contexts, unless replicated/covered |
| **U** UNKNOWN / VALIDATION DEFINED | Test plan or source unverified | Research question and next step | PASS or FAIL |
| **N** NON-EXECUTION | Admin-block, build/setup/checkout failed before relevant assertions | Harness/permission problem | Negative product result |

**Release invariant:** No finite set of G/S/M/R/H labels automatically upgrades a product to D. A red/green test is only meaningful with exact oracles, source SHA, negative controls and a started/finished execution record. **User data, tokens and flight records must not be copied into open evidence.**

## 2026-11-13 — IndexedDB transaction completion is not custody durability (A → E/C/B/D)

**SOURCE / standard:** [Indexed Database API 3.0 durability hints](https://w3c.github.io/IndexedDB/#transaction-durability) defines `strict`, `relaxed`, and `default` as *user-agent hints*. Under `relaxed`, an implementation may report successful commit after writing to the operating system without verifying persistent-media flush; `strict` may defer completion until that verification. [MDN transaction()](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction) documents the API and [MDN IDBTransaction](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction) identifies abort paths including I/O and quota failures. [Chrome's 2023-11-03 announcement](https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed) says Chromium 121 changed its default to relaxed and explicitly warns that strict is not an unconditional data-loss guarantee. **Platform distinction:** this Chrome default is Chromium-specific; standards do not prescribe one universal default or guarantee managed iPad/WebKit behavior. The precise installed Safari/MDM version remains CHANGE WATCH.

## 2026-11-14 Stage 8 — shutdown, pending writes and transaction completion are separate failure gates (A owner; E/C/B/D transfer)

**SOURCE (2026-11-14, standards-oriented documentation):** [MDN Using IndexedDB — warning about browser shutdown](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB) distinguishes transactions aborted on browser shutdown, unexpected database closure, and the impossibility of reliably finishing a new asynchronous write from an `unload` handler. It recommends keeping logically related clear/write operations within one transaction. [MDN IDBTransaction durability](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability) identifies `strict`, `relaxed`, and `default` as **user-agent durability hints**, not an independent export or a guarantee against eviction. These are general platform facts, **not evidence that the locked Sembast Web adapter selects any particular mode**.

**SYNTHESIS / distinct failure boundaries:** (a) an edit still in UI memory when a tab is closed; (b) an asynchronous write initiated but not yet completed when a document terminates; (c) a transaction that aborts, with no committed new state; (d) a transaction whose completion event is observed but whose bytes are not independently recoverable after power loss, eviction or origin removal; and (e) a cross-tab optimistic callback replay. These five states require different oracles. In particular, `beforeunload` prompting or `visibilitychange` best-effort persistence is **not a substitute** for a completed transaction and verified independent Files restore. An `onclose` handler may observe unexpected database closure in supporting browsers, but cannot retroactively commit an aborted transaction or guarantee that UI notification is delivered before process termination.
