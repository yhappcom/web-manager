## 1. HISTORY / PROBLEM → PRINCIPLE → STANDARD

AppCache's inflexible declarative lifecycle led to programmable Service Workers. Programmable interception creates a new duty: navigation, immutable resource caching, action-bearing URLs, Worker updates, local data migration and current remote authority are separate state machines. A successful cache lookup does not prove a safe response, and a successful Worker registration does not prove an offline-capable build.

**SOURCE (primary, checked 2026-10-11):**
- Flutter Web FAQ (updated 2026-09-21, Flutter 3.47 scope): https://docs.flutter.dev/platform-integration/web/faq — default generated caching Worker retired; newer Flutter writes a self-cleaning stub, requires app-owned Worker for offline, and documents a Firebase SPA-rewrite exclusion for missing assets/compiled entry points.
- Flutter web initialization: https://docs.flutter.dev/platform-integration/web/initialization — generated `flutter_bootstrap.js`, customizable bootstrap, Worker configuration; source `web/index.html` is not a substitute for generated bytes.
- Firebase Hosting reserved namespace: https://firebase.google.com/docs/hosting/reserved-urls — `/__` is reserved for Firebase and must not be intercepted by PWA navigation fallback; reserved Hosting SDK scripts are for Firebase JS SDK v8 and earlier, while auth helpers still use the namespace.
- W3C Service Workers 2026-09-17 CRD: https://www.w3.org/TR/service-workers/ ; WHATWG URL https://url.spec.whatwg.org/ ; Fetch https://fetch.spec.whatwg.org/ ; MDN Cache.match https://developer.mozilla.org/en-US/docs/Web/API/Cache/match . Specification ≠ uniform Chromium/WebKit implementation.
- MDN fetch event: https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/fetch_event — a fetch listener without `respondWith` does not by itself substitute a network response. Registration scope alone is not interception evidence.

## 3. SYNTHESIS — five independent risk planes

**R1 — release provenance:** CI green, acceptance-mode marker, normal-build success, immutable artifact digest, deployed bytes and installed runtime are six different evidence claims. Record source SHA, toolchain, lockfile, command, exit status, generated bootstrap/Worker/imports, asset digest and Hosting version separately.

**R2 — route and cache-key safety:** `ignoreSearch: true` can collapse distinct action-code URLs when used against them; globally removing `?` is unsafe outside a verified immutable static-resource allowlist. This is a *conditional failure mode*: whether LogMate's final Worker uses it for sensitive requests remains OPEN. Firebase `/__`, `/auth` action URLs, account APIs and sync endpoints should not receive app-shell substitution or sensitive Cache Storage entries.

**R3 — URL parser equivalence:** URL constructors can normalize encoded dot segments before a path classifier sees them. A synthetic test originally misclassified `/assets/%2e%2e/auth` until the raw ambiguous path was checked before normalization. Compare Hosting routing, URL parsing and Worker policy on a disposable origin; do not call this a product exploit.

**R4 — postprocessor repeatability:** an already-transformed Worker can fail the second transform at exit 4. Clean rebuild may regenerate input and avoid the problem. Engineering should test pristine, already-patched, cleanup-stub and malformed Worker inputs, and distinguish deterministic artifact verification from mutation/retry.

**R5 — data durability and authority:** Worker activation, cache retirement, schema migration, local UID-bound ledger/outbox preservation and remote operation admission are independent. `Clear-Site-Data: "storage"` is not a routine Worker repair for unique unsynced offline records (see research/322). An old offline iPad can remain useful locally without gaining current remote authority.
