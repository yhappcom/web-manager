## 9. Browser-process provenance, fixture-identity and execution-failure falsification (2026-10-25) [SOURCE / VALIDATION / SYNTHESIS]

### 9.1 Why a plausible DOM is not browser execution evidence

A second review of the committed §8 Chromium laboratory identified a distinct **research-tool false-green opportunity**: `runLab()` called `classifyDom(result.output,id)` regardless of the Chromium subprocess outcome. The DOM-only classifier was intentionally pure for unit tests, but a crashed or nonzero Chromium process that emitted a plausible `<pre id="probe-result">` fragment could be labeled PASS. The runner also accepted a DOM result without checking whether the requested **case-specific fixture document** was returned. This is an evidence-admission weakness, **not** an observed CSP bypass or a LogMate product incident.

The remediation is narrow and fail-closed. The new `classifyBrowserOutcome(outcome,id)` requires `reason === 'COMPLETED'`, a browser DOM containing a server-issued `<meta name="fixture-case" content="...">` marker for that exact case, and then the original positive/negative execution and violation-event oracle. `CHROME_NONZERO`, `CHROME_TIMEOUT`, `OUTPUT_LIMIT`, `CHROME_START_ERROR`, absent process evidence and wrong fixture identity can no longer become a runtime PASS. Non-completion is **UNKNOWN**; completed but wrong/missing fixture identity is **FAIL**. This preserves the crucial distinction between a browser not running and a browser executing the wrong thing.

The server now places a case-specific marker in each served document, rather than trusting the test caller's requested ID. The marker is **not** a cryptographic signature, remote-origin authentication or proof of the HTTP status/headers actually applied to the page. It binds a trusted disposable fixture response to a browser DOM in this local laboratory only. For product admission, independently freeze origin, response headers/body hashes, navigation URL, Worker script digest, browser version and source/build provenance as already required by R01–R10. The expected policy must not be generated from the observed response.

## 15. IndexedDB request-success versus transaction-commit admission (2026-10-25) [SOURCE / CONTRADICTION / VALIDATION / SYNTHESIS]

### 15.1 Failure mode found in the §14 research fixture

The first §14 Worker durability fixture resolved its `ledger(write)` promise from the individual `IDBRequest.onsuccess` callback and closed the database only from `IDBTransaction.oncomplete`. Those events are **not equivalent**. A request may succeed before the containing readwrite transaction commits; a later abort can invalidate the write. Consequently the synthetic controlled-phase result could advance and the Chromium subprocess could exit before the write transaction's successful completion. This was an **evidence-admission bug in the research fixture**, not a demonstrated LogMate defect.

### 19.1 Historical problem → standard → platform behavior [SOURCE / CHANGE WATCH]

- W3C [Indexed Database API 3.0](https://www.w3.org/TR/IndexedDB/) defines a transaction *durability hint*: `strict` may delay successful commit until persistent-medium writes are verified; `relaxed` may acknowledge once changes reach the OS without that verification; `default` follows the browser/storage bucket's policy. The hint is not a hardware/OS/backup guarantee. The transaction `complete` event is a database transaction boundary, **not** a proof of survival through sudden power loss, origin eviction, managed profile deletion, app reinstall or cross-context transfer.
- Chromium's [default durability change](https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed/) says Chrome **121 onward** defaults IndexedDB to `relaxed` for performance; `strict` may be requested for exceptional critical data, but does not guarantee no loss. This is a **Chromium-specific vendor statement**, not proof of LogMate/Sembast's effective transaction options or of Safari/iPadOS behavior.
- [MDN IndexedDB guide](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB) describes historical Firefox relaxed-durability behavior; [MDN durability property](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability) documents the exposed hint and compatibility caveats. Avoid proposing an unreviewed low-level transaction override without Engineering ownership, performance/battery measurements and library compatibility.

### 21.1 Why the boundary matters — history → principle → standards [SOURCE / SYNTHESIS]

A recoverable backup needs *both* (1) a consistent snapshot that can be safely imported without destroying existing unique data and (2) an independently accessible, confidential, integrity-checked copy. A single-file SHA-256 field, a successful export function and a transactionally atomic restore answer different questions. The W3C [IndexedDB 3.0](https://w3c.github.io/IndexedDB/) specifies atomic transaction commit/abort and defines `strict`/`relaxed` durability **hints**; it does not guarantee power-loss survival, user-file custody, absence of data loss outside a transaction or external author authentication. This is distinct from Sembast Web's library-specific transaction-retry semantics (§19.5).

The [OWASP Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) requires a threat model and recommends established authenticated encryption where confidentiality and tamper resistance are needed. [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html) emphasizes the lifecycle and recovery of encryption keys: losing the sole decryption key can make a perfectly retained backup unrecoverable. [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) defines AES-GCM authenticated encryption, **not** a complete product key-recovery or user-identity solution. Apple [Managed Open In](https://support.apple.com/en-gb/guide/deployment/depaa73a4973/web) adds a separate permitted-destination boundary. Sources reviewed 2026-10-26; cryptography/OS policy and browser capability are CHANGE WATCH.

#### 22.1 Why restore trust is different from byte preservation [FOUNDATION → ADVANCED]

A backup carries *source-replica history*; a restored destination is a *new local replica* that has not demonstrated which source operations a remote server accepted or which incoming changes the destination has applied. Physical byte preservation, authenticated remote acknowledgement, destination cursor progress and future eligibility to transmit are four distinct claims. The same `operationId` can be important for idempotent historical replay without proving that a source receipt is a current destination acknowledgement. An offline PWA can preserve such evidence without converting it into online authority.

**Exact code observations [SOURCE]:**

1. #### 23.1 From the problem to the actual execution boundary [FOUNDATION → PRACTITIONER]

A backup file can be valid JSON but operationally unsafe to process on a memory-constrained client. Four distinct checks must not be conflated: (a) the selected file can be opened; (b) its bytes are within a supported resource envelope; (c) its structure, UID, registry and checksum are acceptable; (d) the destination transaction can safely commit and reopen. The SHA-256 checksum answers none of (a), (b) or physical durability. A user-selected file is a local import surface; **there is no inspected remote file-upload endpoint**. An attacker-controlled file delivered through a third-party channel, or a legitimately large ledger, can nevertheless stress the same local parser if the future user-file UI passes it through.

**Exact-source sequence:**

1. The B1 export method traverses **all 37 registry stores** inside one Sembast transaction, materializes every row into in-memory maps/lists, canonically JSON-encodes the complete unsigned object, hashes that string with the in-repo SHA-256 routine, and JSON-encodes the signed-manifest container. It returns the entire backup as a **String**; external Files I/O is not part of this method.
2. The restore API accepts a complete **String**. Before opening its Sembast restore transaction, it calls WholeLedgerBackup.decode, then _validateLbkContainer. The decoder invokes dart:convert jsonDecode on the complete input, creates store maps/lists, and does **not contain an explicit maximum input-byte, row-count, nesting-depth or resource-budget guard**. Its root-key-count check is structural, not a byte cap.
3. Container validation checks format, owner UID, capability, registry, per-store counts, duplicate keys and digest. But it first canonically re-encodes the decoded entire container and calculates a SHA-256 digest; its row-shape/duplicate checks follow this digest calculation. Thus a malformed, wrong-owner or digest-invalid input can consume substantial parse/canonicalization work **before** final rejection.
4. _canonical recursively walks maps/lists and constructs sorted map entries; the SHA routine UTF-8 encodes its complete input and creates an additional padded byte array. The exact peak heap amplification and recursion failure threshold are **not measured** and cannot be inferred from source alone. There is no evidence of a production out-of-memory event.
5. Once admitted, restore uses a single Sembast transaction, preserves the destination replica identity, locks the owner, resets active Sync trust and validates references before commit. This is a valuable **transactional logical rollback boundary**, but a transaction cannot undo an earlier parser process termination or certify device-level power-loss durability.
6. The inspected B1 test file covers malformed/tampered input, duplicate store key, claimed destination, injected transactional rollback, SHA vectors and native-file roundtrip. Its source contains **no named oversized/deep-nesting/large-populated-ledger resource-limit case**. Absence of those tests is a coverage observation, not proof that another unseen integration harness cannot exercise resource pressure.
7. W-013 file selection/pick/share/restore UI is **NOT STARTED**. Therefore the file-picker byte-count admission path and cancellation/progress UX cannot be labeled defective in a shipped UI; the **current codec API itself** is unbounded.

### 26.1 Historical problem → security principle → platform standard [SOURCE / FOUNDATION]

AppCache's opaque update behavior motivated explicit Service Worker install/cache/activate control. LogMate correctly pursues complete verified offline assets and refuses to substitute unverified newer bytes for an old pinned client. The new question is **how much repeated verification work is triggered by an otherwise routine warm startup**, and whether correctness checks compete with the pilot's local-ledger read/write, update and recovery liveness on an EFB iPad.

A byte digest verifies bytes against an expected digest only for the checked buffer; it does not certify deployment provenance, data durability or a future cache read. The browser Cache API stores whole request/response pairs; `Response.arrayBuffer()` reads the body to completion, and `SubtleCrypto.digest()` accepts a complete buffer, not a streaming input. A Service Worker may be terminated for abnormal/overlong operations under the specification; `waitUntil()` extends an event's lifetime but is not a measured Safari/MDM unlimited execution budget. CacheStorage is origin storage, not an IndexedDB transaction or a release authority. None of these generic facts proves an actual LogMate slowdown.

1. Bootstrap registers the owned Worker and requests `registration.update()`. ### 26.3 Failure-chain analysis and non-transitive evidence [SYNTHESIS / CONTRADICTION]

- **Warm repeat amplification:** the app may be fully cached yet perform repeated full-body reads/digests, rather than a cheap metadata check. In a stable current-build case, promotion performs redundant identical full scans before returning a status. This is source-derived; actual startup frequency and duration are OPEN.
- **Foreground contention:** the messages are not awaited by Flutter first paint, but Worker CPU, cache reads and memory allocations can compete with other browser work and local Sembast/IndexedDB activity. There is no evidence yet of dropped frames, flight-entry latency, battery drain, Safari termination or eviction.
- **Serialized critical section:** `PROMOTE_VERIFIED_CANDIDATE` runs the full `inspect` inside the per-global `controlMutation` lock. - **Install/activate liveness:** expensive inspection within `waitUntil` is a lifecycle gate; platform time budgets and failure behavior are browser/OS dependent. An install that does not finish cannot be counted as a successful update, even if old assets remain. An activation that fails cannot be promoted by a green static generator test.
- **Integrity-versus-availability tension:** trusting `verified=true` forever would weaken the existing defense against later same-origin Cache mutation; conversely re-hashing every font and license on every ready/status request can be operationally disproportionate. An authorized redesign must preserve response-byte verification, generation pinning, old-client compatibility, failure-closed promotion and external ledger custody.
- **Scope boundaries:** an offline shell READY flag is not client routing READY (§508), remote Sync success (§515/516), current LBK snapshot (§519 §24), or a proof that the browser has enough resources to re-open a populated ledger. One cached file being verified does not imply the full collection was checked at that same time.

### 27.1 Problem → standard → exact source chain [SOURCE / HISTORY]

The Worker protects *bytes against a particular expected digest*, but the expected digest for a **served historical/current version** is loaded from an origin-writable catalogue. The browser does not treat CacheStorage as an authenticated release-authority store. The W3C Service Workers spec explicitly associates the same origin's window and Worker contexts with the same cache name map; CacheStorage is independent of the HTTP cache and must be managed by origin scripts. MDN confirms that \`Window.caches\` and \`WorkerGlobalScope.caches\` can open the same named cache. The secure-context requirement does **not** make cached JSON immutable or authorize its publisher.

Primary references (consulted 2026-10-26):
- W3C Service Workers current draft, §5 Caches / cache lifetimes: https://www.w3.org/TR/service-workers/
- MDN Cache and CacheStorage.open (window + worker access, origin-scoped persistence): https://developer.mozilla.org/en-US/docs/Web/API/Cache and https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage/open
- OWASP CSP Cheat Sheet (CSP is defense in depth, not an XSS-proof boundary): https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html
- Chromium Service Worker Security FAQ (persistent registration and XSS consequences, **Chromium-specific**): https://www.chromium.org/Home/chromium-security/security-faq/service-worker-security-faq/

**Exact source trace:**
1. \`CONTROL_CACHE='logmate-offline-control-v2'\` and \`CONTROL_KEY='/__logmate_offline_control_v2.json'\`; \`readControl()\` parses a JSON response from CacheStorage and accepts \`schemaVersion===2\` with truthy \`versions\` and \`clientBuilds\`. It does **not** authenticate the release origin/approval or compare stored manifest hashes with an independent anchor.
2. \`versionFor(control, buildId)\` returns \`control.versions[buildId]?.manifest\`; \`shellCache(manifest)\` derives a cache name from **that manifest's** \`appBuildId\`.
3. Root navigation obtains \`control.currentBuildId\` and writes client ID mappings; subsequent asset requests use \`clientBuilds[event.clientId]\`. Both paths then use \`versionFor\` and the stored manifest's shell/font item path, size and SHA-256.
4. \`verifiedResponse(cache,item)\` recomputes the digest over the returned bytes and rejects mismatch. This correctly rejects **asset-only** mutation against an unchanged manifest. It cannot establish that the manifest's expected digest, build ID or current-build pointer was approved by the app publisher.
5. The fetch path does **not** consult \`control.versions[buildId].verified\` before serving; that flag participates in \`promoteInControl\`, not in \`versionFor\`/fetch. A forged stored version + matching cached bytes can therefore satisfy the fetch digest without ever being a Worker-embedded approved candidate.
6. \`status()\` checks the Worker-embedded \`OFFLINE_MANIFEST\` for candidate readiness and the stored \`served\` manifest for served readiness. Those are different evidence classes; a \`ready\` checksum against an attacker-modified stored manifest is not a release-authority proof.

**Threat prerequisite:** an already-executing same-origin script (e.g., successful XSS, compromised allowed third-party bundle, or authorized-but-malfunctioning same-origin app code) able to call \`window.caches\`. An unrelated cross-origin site cannot simply write LogMate's caches. This analysis **does not establish an actual XSS entry point, exploit, affected user, compromised production deployment, or Safari/MDM reproduction**. Such a script may already access the local ledger; the narrower new conclusion is that the Worker checksum is **not an independent trust boundary against that script**.

### 27.3 Expert operational judgment: separate three assertions [SYNTHESIS / MINTTAP DECISION — PROPOSED]

Keep distinct:
- **Byte integrity:** returned bytes match a specified expected digest at the time of reading. Existing \`verifiedResponse\` provides this conditional property.
- **Publisher-approved release membership:** the expected manifest/build and allowed predecessor transition are bound to an independently authenticated release identity, not merely same-origin mutable CacheStorage.
- **Current client admission:** a specific client is assigned to an allowed build and its local schema/dirty data/outbox are compatible. Neither byte integrity nor membership alone proves safe update, rollback or user-data preservation.

**Do not fix this by dropping per-response hashes, trusting \`verified:true\`, calling every stored manifest trusted, clearing the origin, or forcing latest-build fallback for unmapped clients.** Any of those could regress §508 mixed-generation safety or §515 external ledger custody. Do not claim that an authenticated release manifest can protect arbitrary IndexedDB data from an already-running same-origin XSS; that is a different trust boundary. CSP, trusted script supply-chain and least-privilege third-party policy reduce the chance of the prerequisite, but do not magically isolate CacheStorage by API.

Engineering design alternatives to evaluate (none approved for LogMate):
1. For the **active Worker-embedded build**, derive the expected manifest from immutable code rather than from mutable catalogue JSON. For **older concurrently served builds**, retain a release-authorized immutable manifest set or authenticated release transition record that survives Worker upgrades without losing old-client routing. Validate which trust anchor remains independent of writable origin state and which attacks it cannot stop.
2. Separate mutable **client routing/pointer metadata** from **release-manifest authority**. Authenticate membership/transition and constrain allowed versions before any fetch. Do not let a cache-only \`currentBuildId\` elect a never-approved build.
3. Treat \`status\` as multiple explicit predicates: candidate bytes verified, served bytes verified, served release approved, client assigned, ledger/backup state known. Report \`UNKNOWN/REPAIR_REQUIRED\` where evidence is missing, not an undifferentiated READY.
4. Preserve safe old-client access, rollback/schema compatibility and unique local ledger custody during corruption/compromise repair; never equate deleting a poisoned Worker/cache with deleting or repairing IndexedDB, remote auth, outbox, or external \`.lbk\` files.
