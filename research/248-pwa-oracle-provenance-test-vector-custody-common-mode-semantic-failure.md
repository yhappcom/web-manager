## Problem
247 established that historical verifier reconstruction needs isolated execution, immutable dependency identity where possible, negative controls and genuinely independent differential implementations. The adjacent failure is deeper: the **oracle corpus itself can be wrong or poisoned**. A golden vector may have been generated by the same defective implementation under test; a fixture generator may be compromised; multiple implementations may copy the same prose ambiguity, parser, generated schema or sample code; and a large passing corpus may therefore reproduce one common mistake with high consistency.

Central rule: **an oracle is evidence with provenance, custody, scope and failure domains—not truth by label. Bind vectors to exact bytes and expected claim semantics; preserve who/what generated and reviewed them; separate authoritative external vectors from implementation-generated fixtures; map common-mode dependencies across implementations; and treat disputed corpus evidence as scoped uncertainty requiring independent re-derivation, not majority voting or silent regeneration.**

## SYNTHESIS 1 — “golden” is a role, not a trust property
A file named `golden.json`, a fixture checked into Git, or a vector used for years is not authoritative merely because tests depend on it. Record at least corpus/vector identity, exact bytes/digest, claim being tested, expected result, producer/generator identity, source basis, review/approval evidence, creation/version epoch and known dependencies.

Guards: `golden label ≠ authoritative oracle`; `checked into Git ≠ independently derived`; `old fixture ≠ historically correct fixture`.

## SYNTHESIS 2 — separate externally grounded vectors from implementation-generated fixtures
Classify vectors by provenance. Examples: standards/RFC vectors; independently curated reference datasets; independently hand-derived vectors with review evidence; production-derived historical examples; generator-produced fixtures; implementation-self-generated round trips. These classes answer different questions.

A serializer→parser round trip generated by the same library is useful regression evidence but weak evidence that both implement the external format correctly.

Guards: `round trip passes ≠ external semantics correct`; `self-generated expected output ≠ independent oracle`.

## SYNTHESIS 3 — fixture generators are supply-chain components
A vector generator can poison every downstream test without modifying the verifier. Bind generator source revision/artifact, dependencies, parameters, random seed where relevant, schema/canonicalization version and output digest. If generation is performed in CI, preserve the trust boundary and provenance of the generation step separately from the verifier run.

Guards: `fixture deterministic ≠ fixture correct`; `generator signed ≠ generator semantics correct`; `test artifact authentic ≠ expected result accurate`.

## SYNTHESIS 4 — vector custody protects against substitution, not semantic error
After a vector is accepted into a corpus, protect exact bytes and metadata from silent replacement: content digest, immutable/versioned storage where practical, review trail and append/supersede rather than overwrite. But strong custody cannot turn a mistaken expected result into a correct one.

Guards: `custody intact ≠ oracle correct`; `digest matches ≠ expectation valid`; `signature valid ≠ semantic claim true`.

## SYNTHESIS 5 — expected result and rationale need independent provenance
For high-consequence vectors, retain not only input and `PASS/FAIL`, but the rule/derivation that justifies the expectation. Otherwise a poisoned expected result can be copied indefinitely. Where feasible, the expectation should be derivable from a standard, independent calculation, separately implemented reference method, or reviewed historical specification—not solely from the system under test.

Guard: `expected result recorded ≠ expected result justified`.

## SYNTHESIS 6 — implementation independence is a graph property
Two binaries written by different teams can share the same parser package, generated schema, crypto library, canonicalization code, sample implementation, fixture generator, specification interpretation or upstream test corpus. Map these dependencies before counting differential agreement as corroboration.

Useful dimensions include: language/runtime, parser/canonicalizer, crypto primitive/provider, schema generator, source/spec interpretation lineage, fixture corpus/generator, build platform and reviewer/author overlap.

Guards: `different repository ≠ independent implementation`; `different language ≠ independent semantics`; `different binary ≠ different oracle failure domain`.

## SYNTHESIS 7 — common-mode semantic failure can survive large corpora
Thousands of passing vectors do not protect against an untested shared ambiguity. Coverage must be claim-oriented: valid, invalid, malformed, boundary, predecessor/generation substitution, duplicate/ordering/canonicalization cases, signature mutation and historical edge cases relevant to the format. Corpus size is not a substitute for failure-domain diversity or semantic partition coverage.

Guards: `large corpus ≠ broad semantic coverage`; `100% pass rate ≠ specification conformance`.

## SYNTHESIS 8 — disagreement is diagnostic evidence, not a vote
If V1 says accept and V2 says reject, do not choose the majority implementation or the newer implementation automatically. Freeze the disputed vector, exact outputs, logs, versions and dependency graphs; determine which semantic claim differs; then re-derive from stronger independent evidence.

Likewise, three implementations agreeing against one is weak if the three share a parser/generator/spec lineage.

Guards: `majority agreement ≠ semantic truth`; `newest implementation ≠ correct implementation`; `one dissenting oracle ≠ noise`.

## SYNTHESIS 9 — corpus compromise has a time and dependency blast radius
If a fixture generator or corpus maintainer is compromised, do not invalidate every historical result automatically. Identify affected corpus generations, generator versions, custody interval, vector classes and closure claims that actually depended on them. Preserve unaffected independent vectors and contradictory evidence.

Guards: `corpus compromise ≠ every prior test false`; `unknown compromise start ≠ safe pre-compromise boundary`.

## SYNTHESIS 10 — disputed-oracle recovery is re-derivation, not regeneration
When a corpus becomes disputed, regenerating it with the same generator or same specification-derived implementation can reproduce the same defect. Recovery should seek a materially different basis: primary normative text, independent hand derivation/review, external published vectors where applicable, independently implemented parser/canonicalizer, metamorphic/negative relations, and historical artifacts whose expected outcomes were recorded before the dispute.

Record unresolved cases as `ORACLE-DISPUTED` or `SEMANTICS-UNRESOLVED` rather than forcing closure.

Guard: `regenerated corpus ≠ independently recovered corpus`.

## SYNTHESIS 11 — metamorphic tests expose some shared errors but are not authoritative oracles
Relationships such as one-bit signature mutation must fail, truncation must not silently preserve a valid signed object, predecessor substitution must alter lineage outcome, or semantically irrelevant representation changes must behave according to the exact historical canonicalization rules can expose common false positives. They do not independently determine every expected result and can themselves encode a mistaken assumption.

Guard: `metamorphic property holds ≠ full semantics proven`.

## SYNTHESIS 12 — historical semantic validity remains separate from current authority
A recovered corpus may establish with bounded confidence that a G12 verifier interpreted an object according to G12 rules. It does not authorize G12 data to mutate G19 state. Historical reconstruction remains an evidence-analysis path; current bootstrap, current policy and operation-level re-admission remain separate.

Guards: `oracle recovered ≠ authority recovered`; `historical PASS ≠ current admission PASS`.

## SYNTHESIS 13 — LogMate/EFB long-offline rejoin under disputed oracle evidence
For a company iPad returning with unique flight/logbook data and G12 evidence while current authority is G19:
1. preserve original local data/evidence bytes and provenance;
2. establish current bootstrap without using G12 verifier authority;
3. assess G12 evidence only in the isolated historical path;
4. if the G12 corpus/generator is disputed, preserve the dispute and seek independent re-derivation;
5. check lineage/fork/splice with current trusted context;
6. migrate schema/data without rewriting original evidence;
7. re-admit queued operations individually under current policy.

Do not reset the device merely to remove ambiguous evidence; do not put a legacy verifier or disputed fixture corpus into the current Service Worker/app shell to make sync succeed.

## SYNTHESIS 14 — privacy-minimized corpus retention
Oracle provenance normally needs vector identity, exact input/output where necessary, semantic rationale, generator/reviewer provenance and dependency context—not unrelated user telemetry. Production-derived fixtures should be minimized/de-identified where possible and retained only when necessary for the claim and policy/legal basis.

Guard: `debugging value ≠ unlimited retention justification`.

## SYNTHESIS 15 — corpus promotion is a governed transition
A new vector should not silently become normative merely because one developer adds it. Promotion should record source class, semantic claim, expected-result rationale, review status and supersession relationship. Correcting a bad vector should preserve the old vector and affected-test lineage when needed for incident analysis rather than rewriting history.

Guard: `test merged ≠ oracle promoted`; `vector corrected ≠ historical result rewritten`.

## MINTTAP DECISION / DIRECTION
Generic policy only; product implementation remains OPEN.

1. Treat oracle corpora and fixture generators as provenance-bearing evidence assets.
2. Classify vectors by source/independence strength; never collapse all fixtures into one “golden” class.
3. Content-bind vectors and preserve expected-result rationale plus generator/reviewer provenance where consequence warrants it.
4. Map shared parser/generator/specification/library dependencies before claiming differential independence.
5. Preserve disagreements and disputed corpus generations; use re-derivation rather than majority vote.
