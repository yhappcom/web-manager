## 2. Primary sources and standards [SOURCE / CHANGE WATCH]
- [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2): an HTTP POST is not automatically idempotent merely because a caller retries. An application-specific stable operation identity and server receipt are necessary to safely reconcile an unknown result.
- [Firebase Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions): transactions are atomic; contention can re-execute the transaction function. No external side effect or client-visible ACK should be issued from a replayable callback. Offline transaction limitations are distinct from LogMate local-first edits.
- [Firestore server client libraries](https://firebase.google.com/docs/firestore/client/libraries): privileged server libraries **bypass Firestore Security Rules** and rely on IAM. A client-side deny-all rule is not an authorization check for Admin SDK code. Server endpoints must verify the authenticated principal and current ledger Owner/stream authority before material operations.
- [Firebase App Check enforcement](https://firebase.google.com/docs/app-check/enable-enforcement): app attestation is not a UID Owner grant or immutable operation dedup. Limited-use token replay protection is a distinct, capability- and endpoint-specific control; it cannot replace receipts. Recheck provider/product support before release.
- [W3C IndexedDB 3.0](https://www.w3.org/TR/IndexedDB/): local commit and storage durability do not prove remote acceptance or independent backup. [Chrome relaxed IndexedDB durability](https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed/) is another separate failure class.
- [521](521_stage8_pwa_sembast_cross_tab_replay_wasm_web_opener_admission_20261027.md), [522](522_stage8_offline_utc_lww_clock_trust_and_recovery_admission_20261027.md) and [298](298_pwa_durable_local_state_device_backup_restore_failure_domain_contract.md) own the local replay, UTC identity and restored-binding provenance evidence respectively.

## 3. Security model [SYNTHESIS / CONTRADICTION]
The request's owner field, generation, replica ID, original modifiedAtUtc, operation ID and digest are **untrusted data** until an authenticated server checks their meaning against current authority. A client-reported generation is only a stale-client hint; it is **not proof of a current grant**. A same-ID/same-digest receipt can describe a historically accepted operation, but **must not become a new authorization grant after deletion/revocation/Owner transfer**. A server should decide explicitly whether a previously accepted receipt may be disclosed to a revoked caller; this fixture takes the conservative deny-before-replay path.

**Critical independent layers:**
1. Transport request and authenticated subject (Firebase ID token verification in the real product; synthetic token lookup in the lab).
2. Current UID Owner, stream status and authority generation, checked at material admission and reads.
3. Immutable original operation ID/digest and per-Owner receipt/sequence within a transactional uniqueness boundary.
4. Record winner comparison by **original** UTC microseconds, not server arrival sequence. Preserve losing revisions and tombstones.
5. Client response/ACK receipt; response loss creates **UNKNOWN**, not proof of noncommit.
6. Local Pull/Apply and contiguous applied cursor; only actual successful Manual Sync may update lastSyncAt.
7. Independent LBK export/restore and managed iPad data custody, not inferred from any server response.

**Potential defect found during synthetic design:** a globally keyed operation receipt that checks digest but fails to bind the **original receipt Owner** can return a prior Owner's receipt after ownership changes. The fixture explicitly rejects this in RA09. This is a *model design counterexample*, **not** an observed LogMate/Firebase vulnerability. The production data key/tenant scope is OPEN.

### Standards and official platform constraints [SOURCE / CHANGE WATCH]

- [Firebase Auth emulator connection](https://firebase.google.com/docs/emulator-suite/connect_auth): `FIREBASE_AUTH_EMULATOR_HOST` routes Admin SDK verification to the Auth emulator and accepts its **unsigned test tokens**. This variable **must never be set in production**. The emulator's token-verification success is not a production signature/issuer/audience/revocation test.
- [Firestore emulator connection](https://firebase.google.com/docs/emulator-suite/connect_firestore): `FIRESTORE_EMULATOR_HOST` routes Admin SDK to a local emulator. Emulator transaction/index behavior differs from production. In particular, implicitly created **named databases can have open rules**; the fixture explicitly targets the default database and ships deny-all rules.
- [Firestore Security Rules testing](https://firebase.google.com/docs/firestore/security/test-rules-emulator): rules must be loaded explicitly; absent rules can leave emulator projects open. A client REST negative test must confirm denial on the exact target database, not merely infer denial from a rules file.
- [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions) and [transaction serializability](https://firebase.google.com/docs/firestore/transaction-data-contention): read-before-write, callback retries and commit-time serializability matter for immutable operation admission. Emulator contention and production multi-region behavior are **not interchangeable**.
- [Firestore server SDK/IAM boundary](https://firebase.google.com/docs/firestore/client/libraries): privileged server libraries bypass Security Rules. A client deny-all rule does **not** authorize a server function. The verified subject and current ledger Owner must be checked **inside the material transaction**.
- [RFC 9110 idempotent methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2): the transport cannot tell a caller whether a response-lost POST committed. The server's immutable receipt is an application contract, not an HTTP property.
- [Firebase App Check enforcement](https://firebase.google.com/docs/app-check/enable-enforcement): app attestation may add abuse resistance, but neither App Check nor a verified UID alone is a current ledger Owner grant. Endpoint-specific replay/attestation support remains CHANGE WATCH.

### 14.2 History, standard and operational boundary [SOURCE / SYNTHESIS]

The same-origin policy restricts cross-origin response access; the [WHATWG Fetch Living Standard](https://fetch.spec.whatwg.org/) (updated 2026-10-19 at review) defines CORS and preflight. Cross-origin POST using Authorization and application/json normally causes an OPTIONS preflight naming the requested method and headers. **Preflight carries no bearer token**; a server must decide CORS policy there without interpreting it as a user operation. The actual POST still needs authentication and authorization. See [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) and [preflight](https://developer.mozilla.org/en-US/docs/Glossary/Preflight_request).

**Distinct control layers:**
1. **CORS/origin:** browser sharing/preflight policy; not authentication, not a firewall against curl/native/nonbrowser clients. Exact scheme/host/port matters; Origin null and loose suffix matching are unsafe allowlist assumptions. Dynamic origin responses need Vary: Origin when relevant.
2. **Auth:** validate Firebase ID-token signature/audience/expiry, and explicitly decide disabled/revoked session policy. [Firebase Admin ID-token docs](https://firebase.google.com/docs/auth/admin/verify-id-tokens) say ordinary token verification does not check revocation by default. FE17's unexpected disabled-user result was **Auth Emulator-specific**, not a production permission to omit status-aware verification.
3. **Current Owner:** verify active ledger, UID and generation **inside** the same transaction that admits an operation; do not disclose old receipt to a former Owner. A valid UID token alone does not confer ledger ownership.
4. **Payload/receipt:** recompute a real canonical operation digest server-side, enforce same-ID/same-digest replay, changed-digest conflict, immutable receipt and sequence. FE19's ASCII fixture hash is not LogMate wire compatibility or a signature.
5. **App attestation:** [Firebase App Check callable Functions](https://firebase.google.com/docs/app-check/cloud-functions) can enforce app tokens, optionally limited-use replay protection, but it does not authenticate a user or Owner. Extra token-verification latency/cost/quota and old-client compatibility need explicit rollout decisions.
6. **Caching:** HTTPS and Cache-Control: no-store / fetch cache no-store are HTTP-cache controls ([MDN Request.cache](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache)); they do **not** prove a controlling Service Worker cannot deliberately store or synthesize an authenticated response through CacheStorage.

**CSRF versus bearer:** Cookie-based ambient authority can be sent by a browser without the application's explicit authorization header and requires appropriate CSRF mitigations (Origin/CSRF token/SameSite and policy). A JavaScript-supplied bearer in Authorization is not automatically attached by an unrelated site, but XSS/token theft and server authorization remain threats. CORS does not replace CSRF defenses for a cookie-authenticated endpoint. [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) explicitly cautions against permissive subdomain allowlists, null Origin and missing source-origin evidence.

### 15.1 History → design principle → primary standards/platform [SOURCE / CHANGE WATCH]

Traditional server-centric logout often clears browser session state and cached private responses. Offline-first PWA changes the data model: the browser origin can hold the **only working copy of a user's unsynchronized flight ledger**, not merely a cache of remote data. Therefore, **credential invalidation, local ledger access lock, data deletion, and independent backup are four separate operations**. The blanket "clear all site data on logout" recipe is unsafe for a locally authoritative ledger.

Primary/current evidence reviewed 2026-10-29:
- [Firebase Auth Web persistence](https://firebase.google.com/docs/auth/web/auth-state-persistence), page updated **2026-10-21 UTC**: LOCAL persists across browser closure and synchronizes same-origin tabs; SESSION is tab/session scoped; NONE is memory-only; default browser behavior is LOCAL when supported. Firebase explicitly distinguishes Auth persistence from Firestore offline persistence. **This documents the JavaScript SDK, not a measured Flutter Web FirebaseAuth persistence setting.**
- [Firebase Admin session management](https://firebase.google.com/docs/auth/admin/manage-sessions): locally present ID tokens and refresh-token revocation are different; server-side revocation checks require the documented additional validation path. A locally restored currentUser is not proof of current server Owner authority.
- [WebKit Safari 17.2 Home Screen](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/): at Home Screen creation, login **cookies** may be copied once, but **other local storage is not**; subsequent web-app and Safari data do not share a store. This does **not** certify MDM Web Clip behavior or all future iPadOS releases.
- [MDN Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data): the "storage" directive deletes IndexedDB and unregisters service workers; the "*" wildcard broadens clearing. MDN gives an ordinary logout example using "cache", "cookies", "storage", etc. **That example is not safe to adopt wholesale for LogMate** because its Web ledger is IndexedDB-backed.
- [Firebase App Check callable enforcement](https://firebase.google.com/docs/app-check/cloud-functions) and [2nd-gen callable options](https://firebase.google.com/docs/reference/functions/2nd-gen/node/firebase-functions.https.callableoptions): App Check proves a different property from user UID authorization; consumed limited-use token state is exposed to the handler and does not by itself implement immutable Operation/Receipt idempotency. Replay protection adds a verification round trip and has rollout/latency implications.
- [Firebase Service Worker sessions](https://firebase.google.com/docs/auth/web/service-worker-sessions) documents an **optional** Auth-token management pattern. Its existence does not mean the current LogMate generated Worker implements it.
- [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) is useful for XSS/token exposure, explicit logout, and session invalidation, but a server-session cleanup pattern must be adapted to an offline-first user-data store.

### 15.3 Five independently owned states [SYNTHESIS / OPERATIONAL JUDGMENT]

1. **AUTH_PRESENT**: Firebase client has a locally restored session. This is not a fresh server grant, not Owner match, not a guarantee of token validity, and not data durability.
2. **LEDGER_OWNER_MATCHED_AND_UNLOCKED**: durable local Owner binding and local lock permit access under the product's offline policy. This is not a server Sync grant. A different UID is a hard mismatch, not a migration opportunity.
3. **REMOTE_AUTHORITY_ACCEPTED**: backend verifies current authenticated subject, revocation/disabled/deletion state and current ledger Owner/generation. An Auth token, App Check token or Origin header alone is insufficient.
4. **REMOTE_OPERATION_ACCEPTED**: immutable Operation ID/digest and current Owner checks result in a durable receipt; lost ACK remains UNKNOWN. This is not a local Apply/Cursor commit.
5. **DATA_CUSTODY_VERIFIED**: independent external file readback plus semantic restore of the 37-store ledger, or a separately proven remote recovery path. Neither LOCAL Auth persistence nor a cached Worker shell meets this predicate.

A disconnected EFB may satisfy #2 while #3 is temporarily unobservable. It must not fabricate #3–#5 or start an unrequested background Push/Pull. An offline-auth outage is not an instruction to wipe data; a confirmed wrong UID/deletion lock is not a license to show another Owner's ledger.

### 15.4 Browser containers, persistence, and cross-tab hazards [A → E / CHANGE WATCH]

- Same-origin browser tabs may share Firebase Auth LOCAL state and Sembast Web IndexedDB, but an explicit sign-out in one tab must be verified against a second tab with an already rendered sensitive screen and in-flight transaction. Auth synchronization is not a proof of immediate local UI redaction or durable lock propagation.
- Switching Firebase Auth LOCAL↔SESSION/NONE has documented cross-tab consequences; no app should infer that one browser profile's Auth mode also determines ledger storage lifecycle.
- Safari tab → user Home Screen installation is a **new data-custody boundary**: cookie copy is not ledger copy; even a successfully copied cookie does not carry the Firebase SDK's script-storage session or the 37-store IndexedDB ledger. The exact Firebase Flutter Web provider behavior must be measured, not inferred from the cookie rule.
- Managed Web Clip, user Home Screen and Safari tab are separate acceptance targets. Managed device policy, browser engine version, OAuth redirect/popup, cookie transfer, storage persistence, local owner binding and file export may differ. No unattended direct P2P, background Sync or hotspot guarantee follows from installability.

### 15.5 Revocation, App Check and response ambiguity [E / A / C]

- Firebase refresh-token revocation is not a magic synchronous offline notification. A disconnected client may have locally readable data under the approved offline policy; the next online privileged request must independently verify current authority. Do not call a network failure a revoked account.
- A signed-out or revoked user's **old receipt** must not authorize new writes or leak another Owner's receipt. Server-side UID, ledger Owner/generation and receipt ownership checks remain mandatory even with a valid App Check token.
- If callable App Check replay protection is enabled, a repeated request may need a **fresh limited-use App Check token** while preserving the **same original Operation ID/digest** for safe idempotent reconciliation. An already-consumed App Check token is not evidence that the operation committed; a new App Check token is not a new user edit. The handler's alreadyConsumed decision and server receipt state must be tested independently.
- Do not silently replace Manual Sync with a service-worker token-interception architecture. The current Worker is shell-focused; adding Auth handling increases credential exposure, route, cache and deployment requirements. Any future privileged response must remain outside shell CacheStorage.
- Authentication failure, App Check rejection, Owner rejection, lost ACK, local Apply failure and verified backup completion need separate status/error codes and privacy-safe observability. Never log tokens, UID, ledger payload or backup bytes.

### 16.2 History → standard → implementation differences [SOURCE]

1. **BFCache is not the HTTP cache.** A browser may freeze and later restore a complete DOM and JavaScript heap without network revalidation. A private frame can therefore outlive the Auth session that originally authorized its rendering. Source: Chrome/web.dev BFCache, **updated 2026-10-16**, https://web.dev/articles/bfcache .
2. **Observe the correct lifecycle.** pageshow runs on both initial load and history restoration; event.persisted=true is the positive BFCache-restoration oracle. pagehide.persisted=true is only an intent to cache, not proof of a later hit. Chrome-specific freeze/resume event behavior is not a universal Safari/WebKit contract. Source: https://developer.mozilla.org/en-US/docs/Web/API/Window/pageshow_event .
3. **A tab broadcast is not durable authority.** Chrome's sign-out guidance recommends pageshow/pagehide and BroadcastChannel to reconcile multiple tabs, but a frozen/discarded/not-yet-created or separately installed context cannot be assumed to have processed a transient message. The durable local owner lock must be checked again on re-entry; a broadcast is a latency optimization, not the security source of truth. Source: https://web.dev/articles/sign-out-best-practices (updated 2023-12-04).
4. **Firebase Auth persistence is not a UI/ledger gate.** LOCAL state can synchronize across browser tabs, while SESSION/NONE behave differently; changing persistence may sign out other tabs. These are SDK persistence rules, not evidence that a previously rendered Flutter route has atomically reconciled local Owner metadata. Firebase primary page **updated 2026-10-21**: https://firebase.google.com/docs/auth/web/auth-state-persistence .
5. **No-store and diagnostics are not universal guarantees.** Chrome BFCache eligibility for no-store documents has evolved. PerformanceNavigationTiming.notRestoredReasons is Chrome-oriented and limited-availability; a null diagnostic does not mean a BFCache hit. ### 19.3 Platform standard versus deployment choice [A owns reusable foundation; E consumes]

- **Origin = scheme + hostname + port, not URL path.** Under the Web same-origin policy, https://minttap.app/site and https://minttap.app/logmate are the same origin, even if each uses different route prefixes. IndexedDB and CacheStorage are origin-governed; separate paths, manifest names and Worker scopes do **not** create independent script-storage principals. Different hosts such as https://minttap.app and https://logmate.minttap.app are different origins (assuming HTTPS/default ports). Primary sources: [MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy), [MDN storage quota/origin](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
- **Worker scope is a navigation/fetch-control boundary, not a same-origin data ACL.** The registration scope selects controlled documents; a window on the same origin can use CacheStorage and other origin storage independently of which Worker controls its navigation. Sources: [ServiceWorkerContainer.register](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register), [CacheStorage](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage). A Worker fetch whitelist is valuable but cannot neutralize arbitrary script execution on the app origin.
- **Threat distinctions:** (a) honest-but-stale tab after sign-out requires durable Owner recheck, masking and transaction-time enforcement; (b) XSS/compromised same-origin third-party script can use the origin's browser privileges and requires script-supply-chain, input and CSP defenses plus origin isolation; (c) unrelated hostile cross-origin site is constrained by SOP, but API authorization still belongs server-side; (d) device seizure, MDM policy and browser storage eviction are different failure domains. Do not label a local lock as cryptographic confidentiality or use CORS as an XSS defense. Source: [MDN CSP and XSS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP).
- **Hosting separation is feasible in principle, not approved for this product.** [Firebase Hosting multisites](https://firebase.google.com/docs/hosting/multisites) and [custom domains](https://firebase.google.com/docs/hosting/custom-domain) document separate Hosting sites/domains, including sites in one Firebase project. Sharing a Firebase project does not merge browser origins. However Auth redirect/cookie domain, cross-origin API/CORS, Service Worker script/scope, DNS/TLS, CSP and operational ownership must be validated for the actual deployment.

### 22.1 Why the distinction matters [HISTORY / DESIGN PRINCIPLE / SOURCE]

Service Workers replaced AppCache's implicit page-centric offline cache with an explicit, origin/scope-controlled fetch handler. A handler can choose not to intercept a document navigation, yet still intercept **subresource requests issued by the resulting controlled document**. A static legal/support page living under the same root-scoped Worker as an offline-first application is therefore **not isolated merely because its navigation request bypasses \`respondWith\`**. The Worker's per-client version-assignment policy and its route bypass policy must agree.

- [MDN fetch event](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/fetch_event): navigation and document subresources both enter fetch handling; when \`respondWith\` is not called, normal network handling applies.
- [MDN Service Worker registration scope](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/scope) and [Using Service Workers](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers): a root registration may control multiple unrelated paths on the same origin; scope is **not** a privacy boundary between those paths.
- [MDN FetchEvent resultingClientId](https://developer.mozilla.org/en-US/docs/Web/API/FetchEvent/resultingClientId): navigation may create a new client ID; subresource fetches have no new resulting-client ID. A mapping established for a root app navigation cannot automatically be assumed for a later non-root public document.
- [Firebase Hosting configuration](https://firebase.google.com/docs/hosting/full-config): static directory index URLs and trailing slash behavior require exact deployed-response checks; tracked canonical link is not a verified live redirect.

### 23.2 Mechanism and standards: why the result is coherent [SOURCE / A→E TRANSFER]

[W3C Service Workers §4.6](https://www.w3.org/TR/service-workers/) distinguishes \`FetchEvent.clientId\` (initiating client) from \`resultingClientId\` (reserved client of navigation); the latter is empty for subresources. [MDN fetch event](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/fetch_event) confirms that both navigation and subresource fetches may be intercepted and that not calling \`respondWith()\` leaves the default network handling in place. [MDN resultingClientId](https://developer.mozilla.org/en-US/docs/Web/API/FetchEvent/resultingClientId) describes the navigation-created client. The exact platform distinction is **navigation route control ≠ all subresource policy**.

The current LogMate [source-generated Worker](https://github.com/yhappcom/logmate/blob/2f78e731/tool/pwa_precache.dart) returns early on a non-root navigation but intercepts other same-origin GETs, resolves \`control.clientBuilds[event.clientId]\`, and can synthesize **503 before checking whether the resource is in the shell manifest**. This makes \`/public.css\`, favicon, touch icons and Auth Action font requests relevant even when the public document is network-served. A root \`clients.claim()\` is control admission, **not** assignment of an app build to every public document. The real Worker stores the mapping in a shared CacheStorage JSON control catalogue; the fixture uses a simpler in-memory mapping and cannot reproduce catalogue races, restarts or version verification.

**HTTP caching is not the answer:** The synthetic server sent \`Cache-Control: no-store\`, yet its Worker still returned a generated 503 because the fetch handler chose to answer. In LogMate, the Hosting config's no-store header does not override \`respondWith()\` or force public CSS to bypass Worker logic. Conversely, blindly allowing network fallback for **private version-pinned Flutter shell assets** could defeat the older-client verified-byte guarantee. The correct policy must separate public-site resource ownership from version-pinned app-shell ownership, not merely replace 503 with unconditional network fallback.
