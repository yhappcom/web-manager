## Problem

278 made acceptance-boundary completeness a continuously maintained assurance claim. That creates a new question: **who or what is allowed to assert that the topology changed, that a discovered path is legitimate, or that the attested boundary set is complete?**

A compromised deployment pipeline, discovery agent, CMDB, gateway inventory, telemetry collector or attestation signer could otherwise create a malicious path and then make the same failure domain certify that path as normal. A cryptographically signed false statement is still false if the signer or its inputs are compromised.

Central rule: **topology evidence needs provenance, authenticated lineage, scoped authority and contradiction handling. No discovery or attestation component may become an unbounded super-root merely because it can observe, sign or publish topology. Evidence authenticity, evidence accuracy, authority to change production, and authority to declare a boundary legitimate are separate claims.**

SLSA defines provenance as verifiable information describing where, when and how an artifact was produced. Its Build track distinguishes merely having provenance from signed provenance generated by a hosted platform and from a hardened build platform. The provenance model also makes the builder identity represent the trusted build platform/control-plane boundary.

**TRANSFER VALIDATION:** topology attestations are not SLSA build provenance. The transferable principle is that provenance is meaningful only relative to the trusted producer/control plane and downstream expectations; a signed document is not self-authenticating organizational truth.

### Transparency witnessing — consistency is not semantic legitimacy

Transparency systems distinguish append-only/global-consistency witnessing from ecosystem-specific verification of whether logged content is legitimate. Witnesses can help detect split views while not determining that a logged artifact or statement is semantically authorized.

Source: https://blog.transparency.dev/can-i-get-a-witness-network

**TRANSFER VALIDATION:** this is useful precedent for separating `everyone saw the same topology statement` from `the topology statement is authorized/correct`. It does not require a transparency log or witness network for MintTap/LogMate.

## SYNTHESIS 1 — authenticity, accuracy, authority and completeness are four different claims

For a topology statement T:
1. **authenticity** asks whether T came from the claimed source;
2. **accuracy** asks whether T faithfully describes what that source observed;
3. **authority** asks whether the source is allowed to authorize the production change or legitimacy classification;
4. **completeness** asks whether material topology is omitted.

A signature mainly helps with authenticity/integrity. It cannot by itself establish the other three.

Guards:
- `signature valid ≠ statement accurate`;
- `statement accurate ≠ source authorized to normalize path`;
- `authorized source ≠ topology complete`;
- `attestation present ≠ attestation sufficient`.

## SYNTHESIS 2 — change-event provenance must bind intent, execution and observed effect

A material change claim is stronger when it can connect distinct facts such as:
- reviewed/authorized change intent;
- source/configuration revision;
- build/deployment artifact identity;
- deployment target/environment;
- deployment/change generation;
- observed resulting route/job/service topology;
- consequence classification;
- verifier/attester identity and policy generation.

These need not be one monolithic object. The important property is a reviewable lineage that prevents a malicious runtime discovery event from silently laundering itself into approved intent.

Guards:
- `deployed ≠ approved`;
- `approved commit ≠ deployed artifact`;
- `artifact provenance valid ≠ deployment target correct`;
- `deployment event authentic ≠ resulting topology fully observed`.

## SYNTHESIS 3 — the producer of a change should not be the sole authority that certifies its legitimacy

If one CI/CD identity can create a new privileged worker, publish the inventory update and issue the only topology attestation accepted by policy, compromise of that identity collapses prevention and assurance into one failure domain.

Independence is consequence- and threat-model-specific. Useful separation can come from policy-verification control, provider/runtime observation, separately governed inventory, bounded active negative probes or other evidence outside the change producer's compromise path. Multiple APIs backed by the same control plane are not independent.

Guards:
- `three feeds ≠ three trust domains`;
- `CI says deployed + CI says compliant ≠ independent verification`;
- `separate key IDs ≠ separate administrative failure domains`.

## SYNTHESIS 4 — discovery feeds are evidence channels, not authority-election channels

A discovery agent can legitimately report `worker X exists`. It should not thereby decide `worker X is an approved current acceptance boundary`. Likewise gateway logs, DNS/service discovery, cloud inventory and telemetry can discover contradictions without being empowered to normalize them.

Newly discovered material paths should resolve against authenticated change lineage and current policy. If lineage cannot be established, the path remains UNKNOWN with consequence-proportionate containment.

Guards:
- `discovered ≠ approved`;
- `observed in production ≠ legitimate production member`;
- `known to CMDB ≠ authorized by policy`;
- `UNKNOWN ≠ malicious ≠ NORMAL`.

## SYNTHESIS 5 — poisoned discovery can hide paths as well as add them

A compromised scanner/collector can falsely add benign-looking entries, but omission is equally important. It can suppress a malicious worker, mark a privileged route non-material, falsify last-seen data or claim a retired predecessor no longer exists.

Therefore discovery assurance must include omission resistance through source reconciliation and active challenge where proportionate. A single clean inventory export is not completeness proof.

Guards:
- `no discovery result ≠ no boundary`;
- `scanner healthy ≠ scanner honest`;
- `zero stale traffic ≠ stale acceptance impossible`.

## SYNTHESIS 6 — contradictory evidence is a first-class state

Examples:
- deployment provenance says worker W was not deployed, but runtime inventory observes W;
- gateway config says route R is retired, but an active negative probe reaches a consequence-bearing handler;
- provider inventory reports service principal P removed, but a background job still succeeds with P-derived authority.

Contradictions must be preserved with source/provenance rather than overwritten by last-write-wins normalization. High-consequence effects may need containment until the contradiction is adjudicated.

Guards:
- `newest evidence ≠ most authoritative evidence`;
- `majority of correlated feeds ≠ truth`;
- `contradiction resolved in dashboard ≠ underlying path reconciled`.

## SYNTHESIS 7 — attestation policy is itself authority and needs bounded scope

The component that verifies topology evidence can become a hidden super-root if it may arbitrarily redefine trusted sources, consequence classes, acceptable generations or exceptions.

A robust generic model therefore versions and scopes verifier policy and preserves who/what authorized policy changes. Emergency override remains a bounded capability subject to the recovery/exception lifecycle already established in 260–276.

Guards:
- `attester can verify ≠ attester may redefine authority`;
- `policy update deployed ≠ policy update authorized`;
- `verifier current ≠ verifier policy legitimate`.

## SYNTHESIS 8 — cryptographic provenance cannot rescue a compromised semantic root

If the attestation signer, policy authority and topology producer are all compromised together, signatures can make false statements tamper-evident after signing while still faithfully authenticating the attacker-controlled authority.

Recovery then follows the prior compromise model: preserve evidence/data, fence high-consequence effects where necessary, re-establish trust from a basis outside the compromised failure domain, and prove obsolete authority rejection. The compromised attester cannot self-clear by issuing a fresh `NORMAL` attestation.

Guards:
- `freshly signed after incident ≠ clean`;
- `key rotated ≠ control plane uncompromised`;
- `attester self-clearance ≠ trust restored`.

## SYNTHESIS 9 — transparency/append-only evidence helps anti-equivocation but does not decide legitimacy

An append-only or witnessed history can strengthen detection of deletion, rollback or split-view topology attestations. It cannot establish that a malicious path was authorized merely because the malicious attestation is immutably recorded.

This preserves the earlier distinction between provenance continuity and semantic legitimacy.

Guards:
- `logged ≠ legitimate`;
- `globally consistent view ≠ correct view`;
- `non-equivocation PASS ≠ topology-authority PASS`.

## SYNTHESIS 10 — PWA/Service Worker updates are change events but not organizational authority

Track A contributes browser facts: Service Worker script/version/scope/control state, client version, cache/storage and navigation behavior. A worker update may materially alter API routing, replay behavior or local queue interpretation and should therefore participate in client-runtime provenance where relevant.

But browser installation/update success does not certify server topology, organizational authority or migration currentness.

Guards:
- `worker update authenticated by HTTPS ≠ backend authority transition approved`;
- `new worker controls client ≠ old queued operation authorized`;
- `client build provenance valid ≠ server acceptance path current`.

## SYNTHESIS 11 — long-offline EFB rejoin consumes current topology lineage; it does not extend stale topology authority

A company iPad may return after weeks with old client code, local data, old endpoint knowledge and queued operations. Rejoin should preserve unique flight/logbook records and provenance, obtain current admission/topology expectations from a trustworthy current basis, and reconcile each material operation against current policy/schema/identity.

The client does not need to prove that every topology change during its absence was seen in real time. The authoritative boundary must prevent stale authority from creating effects merely because the client missed events.

Guards:
- `client missed change event ≠ central topology invalid`;
- `client possesses authentic old topology ≠ old topology current`;
- `rejoin failure ≠ delete local record`.

## SYNTHESIS 12 — PITR/rollback must restore data without restoring attestation authority

A backup can contain old inventories, attestation policies, signer mappings and `NORMAL` topology decisions. Restoring those bytes does not make those authority generations current.

Restore/rollback therefore invalidates the currentness claim until reconciled against a rollback-resistant current reference or governed rebootstrap outside the restored failure domain.

Guards:
- `attestation verifies after restore ≠ attestation current`;
- `restored policy internally consistent ≠ current policy`;
- `backup includes signer keys ≠ signer authority restored`.

## Integrated operational model

For a material topology/change event, the generic sequence is:

1. identify authenticated change intent and scope;
2. bind source/config revision and produced/deployed artifact where applicable;
3. record deployment target/generation without treating deployment success as authorization proof;
4. collect resulting topology observations from complementary sources;
5. compare observed topology with authorized intent and current policy;
6. preserve contradictions and UNKNOWNs instead of normalizing them away;
7. apply consequence-proportionate containment to unresolved material paths;
8. issue/retain scoped topology attestation with source provenance and policy/verifier generation;
9. perform bounded predecessor/hidden-path negative probes and periodic independent-enough reconciliation;
10. on restore/rollback/incident, invalidate stale currentness and re-attest from current trust basis.

This is a reasoning model, not a mandated product architecture.

## PWA / LogMate-like application case

Hypothetical only; no production facts inferred.

Suppose a company iPad returns after six weeks offline. During its absence a deployment migrated `sync-v7` to `sync-v8`. A runtime discovery feed now also reports an unexpected background consumer `compat-v7b`, while CI/CD inventory claims only `sync-v8` exists.

Unsafe responses include trusting the CI inventory because it is signed, trusting runtime discovery because it is newer, deleting the iPad queue because it references v7, or allowing `compat-v7b` because it is already deployed.

Generic safe reasoning:
- preserve local unique records/queue/provenance;
- preserve the CI/runtime contradiction as evidence;
- authenticate current change/deployment lineage and verifier policy;
- classify `compat-v7b` UNKNOWN until its intent/authority can be established;
- fence its high-consequence effects if it can materially mutate/publish;
- require current client admission and operation-level reconciliation;
- prove obsolete v7 authority cannot create current material effects;
- retire/quarantine the unexplained path or explicitly authorize a successor only through current governed authority.

`compat-v7b` being visible is not proof it is malicious; it is also not permission to trust it.

## MINTTAP DECISION / DIRECTION

1. Keep Track E as primary owner; this is the current highest-risk bottleneck.
2. Treat topology attestations as scoped evidence with explicit producer/verifier/policy provenance, not as a universal source of truth.
3. Separate deployment authority, discovery observation, attestation signing and policy authority conceptually even when implementation later combines some components.
4. Do not allow a discovery feed to elect authority merely by observing a path.
5. Preserve contradictions and UNKNOWN states; never silently last-write-wins them into NORMAL.
6. Require material restore/rollback/incident events to invalidate stale topology-currentness claims.
7. Preserve unique offline user data and provenance independently of authority uncertainty.
8. Do not infer any MintTap/LogMate CI/CD, signer, provider, OAuth, MDM or backend topology until canonical runtime evidence exists.
