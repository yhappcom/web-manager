# 021 — Release Provenance, Reviewer Authorization & Fail-Closed CI

Status: **PRACTICE / CONTROLLED AUTHORIZATION + PROVENANCE VALIDATION COMPLETED**  
Research date: **2026-09-14**

## Question

Can MintTap make the 020 release manifest operationally trustworthy by binding waivers and manifests to the exact source state and evaluator, authorizing reviewers by issue class, preventing self-approval, and failing CI closed when authorization/provenance is stale or invalid?

This study extends 020 into:

**canonical issue → authorized reviewer policy → source/tool binding → derived manifest → CI allow/fail**.

All records and release examples remain synthetic.

# SOURCE — GitHub controls and provenance

## 1. Required status checks can gate merges

GitHub rulesets can require status checks to pass before merge. GitHub also allows a required status check to be constrained to a specific GitHub App as its expected source.

Primary source, checked 2026-09-14:
- https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets

**SYNTHESIS:** a release-governance evaluator can be made meaningful only when the repository refuses merge/deploy on a failed evaluator result. A green label that is not enforced is advisory, not a release gate.

## 2. CODEOWNERS can require owner review, but one matching owner is sufficient

GitHub documents that branch protection can require Code Owner review, and that approval from any one matching owner is enough for that requirement.

Primary source, checked 2026-09-14:
- https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners

**SYNTHESIS:** CODEOWNERS is useful for file ownership but is not sufficient by itself for MintTap's issue-class authorization model. “May review this file” and “may waive this release blocker class” are different permissions.

## 3. Protected environments can require reviewers and block self-review

GitHub environments support required reviewers and an option to prevent self-review. GitHub documents a maximum of six users/teams in that reviewer list and notes plan/repository-visibility restrictions.

Primary source, checked 2026-09-14:
- https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments

**SOURCE / CURRENT REPOSITORY LIMIT:** `yhappcom/web-manager` is currently private. GitHub's current documentation states that on Free/Pro/Team, required reviewers are only available for public repositories. Therefore environment required-reviewer enforcement must not be treated as an available baseline until the repository/account plan is verified to support it.

## 4. GitHub artifact attestations bind artifacts to workflow/repository/commit context

GitHub artifact attestations use Sigstore and include provenance such as workflow, repository, organization, environment, commit SHA and triggering event.

Primary source, checked 2026-09-14:
- https://docs.github.com/en/actions/concepts/security/artifact-attestations

GitHub also states that private/internal repository artifact attestations require Enterprise Cloud; on Free/Pro/Team they are available only for public repositories.

**MINTTAP CONSEQUENCE:** native artifact attestation is an optional hardening layer, not the current private-repository baseline.

## 5. GitHub OIDC exposes workflow identity and source context

GitHub Actions OIDC tokens expose claims including repository, ref, SHA and workflow context. Current GitHub documentation also states that repositories created after **2026-07-15** use an immutable default subject format containing owner and repository IDs.

Primary source, checked 2026-09-14:
- https://docs.github.com/en/actions/reference/security/oidc

Repository metadata confirms `yhappcom/web-manager` was created on **2026-09-14**, after that cutoff.

**VALIDATION REQUIRED:** before using OIDC as a trust boundary, inspect an actual token/claim template from the workflow rather than assuming the expected subject string.

## 6. Workflow dependencies should be immutable

GitHub's secure-use guidance states that pinning an action to a full-length commit SHA is currently the only way to consume an action as an immutable release.

Primary source, checked 2026-09-14:
- https://docs.github.com/en/actions/reference/security/secure-use

**MINTTAP DECISION:** when release-governance CI is activated, third-party actions in the gate workflow should be pinned to reviewed full commit SHAs and workflow token permissions should be minimized.

# MINTTAP DECISION — reviewer authorization policy

A reviewer registry/policy is versioned independently from a waiver.

Example:

```json
{
  "version": "review-policy:v1",
  "reviewers": [
    {
      "identity": "reviewer:bob",
      "role": "release-manager",
      "allowed_issue_codes": [
        "APPROVAL_STALE",
        "REQUIRED_CONTROL_FAILURE"
      ]
    }
  ]
}
```

A reviewer being known is insufficient. Authorization is evaluated against the **specific issue code**.

Current rule:

```text
known reviewer + allowed issue class + current policy
= eligible reviewer
```

A reviewer permitted for a legal-review class cannot automatically waive a localization/operational blocker.

---

# MINTTAP DECISION — separation of duties

For waiver-based release passage:

```text
approved_by != release_author
```

Self-approval is rejected even if the author is otherwise in the authorized reviewer registry.

This is a MintTap control choice. GitHub's protected-environment “prevent self-review” behavior is supporting platform evidence, not the source of the policy.

Future production work must define:
- what identity is the release author for automated releases;
- whether bot-authored changes require a human approver;
- emergency/break-glass rules;
- whether two-person approval is required for selected issue classes.

# MINTTAP DECISION — source and policy binding

A waiver is valid only against the exact release state it reviewed.

021 binds an effective waiver to:

- `release_ref`;
- `issue_fingerprint`;
- `source_commit`;
- `source_snapshot_digest`;
- `policy_version`;
- reviewer identity;
- expiry.

Changing the commit or normalized snapshot makes the old waiver ineffective even if the human-facing issue label is unchanged.

### Why both commit and snapshot digest?

- commit SHA binds to Git history;
- snapshot digest binds to the normalized control input actually evaluated.

The pair protects against accidentally evaluating a partial/generated input set that does not correspond to the intended source snapshot.

# MINTTAP DECISION — evaluator and manifest provenance

The derived manifest records:

- source commit;
- source snapshot digest;
- reviewer-policy version;
- evaluator name;
- evaluator version;
- digest of evaluation inputs;
- canonical issues;
- applied/invalid waivers;
- decision;
- CI state.

An optional prior `manifest_attestation` can be checked against these fields.

Current PRACTICE rule:

> If an attestation is explicitly supplied and any binding is stale/mismatched, CI fails closed even when the newly computed canonical decision is `PASS`.

This prevents an old “green” manifest from authorizing a newer source state.

# MINTTAP DECISION — CI semantics

The evaluator exposes two related but distinct outputs:

### Governance decision
- `PASS`
- `NEEDS_REVIEW`
- `BLOCKED`

### CI state
- `ALLOW`
- `FAIL`

Current release-CI mapping:

```text
PASS + valid current provenance/authorization → ALLOW

NEEDS_REVIEW → FAIL
BLOCKED → FAIL
invalid waiver → FAIL
stale/mismatched supplied attestation → FAIL
```

This deliberately treats `NEEDS_REVIEW` as a stop condition for release automation. It does not mean the content is necessarily wrong; it means human review is still outstanding.

The command-line practice evaluator exits `0` only for `ALLOW`; all other states exit non-zero.

# IMPLEMENTED PRACTICE

New artifacts:

- `tools/evaluate_release_provenance.py`
- `control/tests/release_provenance_cases.json`

Controlled result:

```text
9 / 9 expected outcomes matched
```

Validated cases:

1. authorized reviewer + allowed issue class + current source/policy → `PASS / WITH_WAIVER`, CI `ALLOW`;
2. unknown reviewer → waiver invalid, release `BLOCKED`, CI `FAIL`;
3. known reviewer but wrong issue class → release `BLOCKED`, CI `FAIL`;
4. waiver bound to old source commit → release `BLOCKED`, CI `FAIL`;
5. waiver bound to old snapshot digest → release `BLOCKED`, CI `FAIL`;
6. release author attempting own waiver → rejected, CI `FAIL`;
7. clean current release → `PASS / CLEAN`, CI `ALLOW`;
8. unresolved `NEEDS_REVIEW` → CI `FAIL`;
9. old evaluator-version attestation supplied for otherwise clean current release → canonical decision remains `PASS`, but CI `FAIL`.

The ninth case is intentional: **canonical truth and authorization-to-deploy remain separate dimensions.**

# PORTABLE CI IMPLEMENTATION DIRECTION

A later active GitHub Actions workflow should conceptually perform:

```text
checkout exact candidate SHA
→ derive canonical snapshot
→ run schema + semantic validators
→ run dependency/approval validators
→ build canonical issue set
→ run release provenance evaluator
→ persist manifest artifact
→ exit non-zero unless ci_state == ALLOW
→ deploy only from the successful job
```

Hardening requirements when activation occurs:

- pin third-party actions to full commit SHA;
- minimal `GITHUB_TOKEN` permissions;
- never allow untrusted PR code to obtain deployment credentials;
- use environment/OIDC controls where supported;
- make the gate a required status check if repository capability permits;
- verify actual OIDC claims before configuring external trust;
- if artifact attestations become available, attest the final deployable bundle/manifest and verify before deployment.

No active workflow was added in 021 because enforcement capabilities and deployment provider are not yet finalized. Activating a workflow prematurely would create operational behavior rather than research evidence.

# DESIGN STUDIO HANDOFF

Future Web Design/Layout-Interaction work should distinguish:

- release decision vs CI authorization state;
- `PASS / CLEAN` vs `PASS / WITH_WAIVER`;
- authorized vs unauthorized reviewer;
- current vs stale source binding;
- current vs stale manifest attestation;
- “review required” vs “hard blocker”.

The primary screen should expose the actionable reason first, while commit/digest/tool/policy provenance can be progressive disclosure. Keyboard/focus/status semantics and long identifiers need real browser validation.

No visual style is prescribed here.
